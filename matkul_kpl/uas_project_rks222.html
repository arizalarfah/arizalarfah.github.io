Project UAS — Threat Modeling & Uji Kerawanan Aplikasi Web

RKS222 Keamanan Perangkat Lunak · Program Studi D4 Rekayasa Keamanan Siber · Politeknik SSN

Semester: Genap 2025/2026 Bentuk kelompok: 4 orang/kelompok Sub-CPMK diukur: 263.1, 263.2, 263.3 (dengan fondasi 261.1) Durasi pengerjaan: 4 minggu Sifat: Take-home, kolaboratif

1 Deskripsi Umum Project

Setiap kelompok (4 orang) berperan sebagai tim security assessment yang ditugaskan mengevaluasi keamanan sebuah aplikasi web. Kelompok wajib melakukan threat modeling, membuktikan kerentanan nyata melalui pengujian teknis (bukan sekadar teori), menghitung tingkat risiko, lalu meremediasi temuan tersebut lewat perbaikan source code sesuai praktik secure coding yang telah dipelajari pada Pertemuan 9–15.

Project ini merupakan sintesis dari seluruh materi satu semester: fondasi threat modeling (STRIDE/DREAD dari Pertemuan 2) diterapkan pada konteks baru — kerentanan aplikasi web (OWASP Top 10, Pertemuan 9–10), lalu ditutup dengan siklus remediasi ala Secure SDLC (Pertemuan 11–14) dan keamanan autentikasi/otorisasi (Pertemuan 15).

2 Tujuan Pembelajaran (Sub-CPMK yang Dinilai)

SUB-CPMK 263.1

Mahasiswa mampu menganalisis kerentanan aplikasi web berdasarkan OWASP Top 10 dan merekomendasikan mitigasi sesuai standar industri.

SUB-CPMK 263.2

Mahasiswa mampu mengevaluasi keamanan autentikasi, otorisasi, dan manajemen sesi pada aplikasi web.

SUB-CPMK 263.3

Mahasiswa mampu menerapkan secure coding practices & alur DevSecOps untuk meremediasi kerentanan yang ditemukan.

Catatan: kemampuan threat modeling (Sub-CPMK 261.1, materi UTS) tetap diukur secara implisit sebagai prasyarat pada tahap awal pengerjaan.

3 Ketentuan Kelompok & Pembagian Peran

Kelompok terdiri dari 4 mahasiswa. Setiap anggota memegang satu peran utama, namun seluruh anggota wajib memahami dan berkontribusi pada semua tahap pengujian — pembagian peran hanya menentukan penanggung jawab utama, bukan pembagian kerja eksklusif.

A

Threat Modeling Lead

  • Menyusun DFD & trust boundary
  • Memimpin analisis STRIDE/DREAD
  • Menentukan prioritas target pengujian
B

Web Application Security Tester

  • Eksekusi pengujian kerawanan web (OWASP Top 10) pada aplikasi target
  • Mengumpulkan bukti (PoC, screenshot, request/response)
C

Secure Code Reviewer & Remediator

  • Code review pada bagian rentan
  • Menulis perbaikan (patch) sesuai secure coding practice
  • Retest pembuktian fix
D

Report & Risk Analyst

  • Menghitung CVSS v3.1 & OWASP Risk Rating
  • Menyusun laporan profesional
  • Koordinasi presentasi
Kontribusi individu dinilai terpisah. Setiap anggota mengisi lembar kontribusi (form singkat berisi tugas yang dikerjakan + commit/log bukti kerja) yang dilampirkan di laporan. Kontribusi tidak seimbang akan memengaruhi nilai individu, bukan hanya nilai kelompok.

5 Ruang Lingkup & Tahapan Pengerjaan

Tahap 1 — Rules of Engagement (RoE)

Kelompok menyusun dan menandatangani dokumen RoE singkat: ruang lingkup target, waktu pengujian, batasan teknik yang diizinkan, dan kontak penanggung jawab.

Tahap 2 — Threat Modeling

  • Buat Data Flow Diagram (DFD) level konteks untuk aplikasi target
  • Identifikasi trust boundary dan aset kritikal
  • Analisis ancaman dengan STRIDE, prioritaskan dengan DREAD

Tahap 3 — Uji Kerawanan Web

  • Buktikan minimal 3 kerentanan dari kategori OWASP Top 10 Web yang berbeda, contoh: Injection (SQLi/XSS), Broken Access Control/IDOR, Broken Authentication/Session Management, Sensitive Data Exposure, Security Misconfiguration
  • Gunakan tools yang sudah dipelajari: Burp Suite dan/atau OWASP ZAP
  • Dokumentasikan setiap temuan dengan bukti (request/response, screenshot, payload yang digunakan)

Tahap 4 — Risk Rating

Hitung skor CVSS v3.1 dan OWASP Risk Rating untuk setiap temuan, lengkap dengan vector string dan justifikasi tiap metrik.

Tahap 5 — Code Review & Remediasi

  • Lakukan code review pada bagian source code yang menyebabkan kerentanan
  • Perbaiki sesuai praktik secure coding (parameterized query, validasi input, enkripsi data, session management, autentikasi/otorisasi yang benar)
  • Tunjukkan perbandingan kode sebelum vs sesudah perbaikan (diff)

Tahap 6 — Retest

Uji ulang setiap temuan pada versi yang sudah diperbaiki untuk membuktikan kerentanan telah tertutup. Sertakan bukti retest di laporan.

6 Deliverables

A. Laporan Tertulis (PDF)

  1. Cover & identitas kelompok (nama, NPM, peran masing-masing)
  2. Ringkasan Eksekutif (Executive Summary)
  3. Rules of Engagement
  4. Threat Model: DFD, tabel STRIDE, skor DREAD
  5. Metodologi pengujian
  6. Temuan kerentanan (per temuan: deskripsi, kategori OWASP, PoC, CVSS/OWASP Risk Rating)
  7. Remediasi (code review + before/after + bukti retest)
  8. Kesimpulan & rekomendasi lanjutan
  9. Lampiran: lembar kontribusi individu, RoE bertanda tangan

B. Source Code / PoC (Repository .zip atau tautan Git)

  • /vulnerable-version — kode asli sebelum perbaikan
  • /remediated-version — kode setelah perbaikan
  • /poc — script/payload pembuktian tiap temuan
  • /evidence — screenshot, capture request-response

C. Presentasi & Demo

Durasi ±15 menit/kelompok: pemaparan threat model, demo live exploit pada versi rentan, demo pembuktian fix pada versi remediasi, dilanjutkan sesi tanya-jawab.
