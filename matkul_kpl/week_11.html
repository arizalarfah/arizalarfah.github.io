Security Debt

Kerentanan yang tidak diperbaiki sejak awal menumpuk menjadi "security debt" — setiap rilis baru memperburuk postur keamanan dan memperbesar biaya remediasi.

Dampak Nyata Kerentanan Kode

🔴 Equifax Data Breach (2017)

Rentan Apache Struts (CVE-2017-5638) yang tidak dipatch — 147 juta data pribadi bocor, kerugian US$700 juta. Akar masalah: SCA tidak dijalankan di pipeline.

🟠 Log4Shell (2021) — CVE-2021-44228

Kerentanan di library Log4j yang dipakai jutaan aplikasi. CVSS 10.0 — Remote Code Execution tanpa autentikasi. Akar masalah: dependency tidak dipantau (SCA tidak ada).

🔵 SolarWinds Supply Chain Attack (2020)

Malware disuntikkan ke build pipeline resmi — 18.000 organisasi terinfeksi. Akar masalah: tidak ada integritas CI/CD dan pemantauan pipeline.

Solusi: Ketiga insiden di atas dapat dimitigasi dengan Secure Coding Practices + DevSecOps pipeline yang tepat.

SCP-01 & SCP-02

Input Validation & Output Encoding

Dua kategori paling kritis — mencegah Injection (A03) dan XSS | OWASP SCP Guide v3

SCP-01: Input Validation

  • Validasi semua data dari sumber tidak terpercaya (form, URL, cookie, header, API)
  • Whitelist approach — izinkan hanya yang diketahui valid (bukan blacklist)
  • Validasi: tipe data, panjang, format, rentang, dan karakter yang diizinkan
  • Tolak atau sanitasi input yang tidak memenuhi spesifikasi
  • Validasi dilakukan server-side — client-side mudah di-bypass
❌ Rentan (Blacklist)
// Mudah di-bypass dengan encoding if (input.contains("'") || input.contains("--")) { reject(); }
✅ Aman (Whitelist)
// Hanya izinkan huruf & angka if (!input.matches("^[a-zA-Z0-9]+$")) { throw "Input tidak valid"; }

SCP-02: Output Encoding

  • Encode semua data yang dikembalikan ke browser sesuai konteks output
  • Gunakan library encoding standar — jangan buat sendiri
  • Tipe encoding berbeda per konteks
Konteks OutputEncoding yang Digunakan
HTML bodyHTML entity encoding (&lt; &amp;)
HTML attributeAttribute encoding (hindari " dan ')
JavaScriptJS Unicode encoding (\uXXXX)
URL parameterURL percent-encoding (%XX)
CSS valueCSS hex encoding (\XX)
❌ Rentan (XSS)
// Input langsung ke HTML echo "Halo, " . $_GET['name']; // Payload: <script>alert(1)</script>
✅ Aman (htmlspecialchars)
// PHP: HTML entity encoding echo "Halo, " . htmlspecialchars( $_GET['name'], ENT_QUOTES, 'UTF-8' );
SCP-03, 04, 05

Authentication, Session Management & Access Control

Mencegah A01 Broken Access Control dan A07 Identification & Authentication Failures | OWASP SCP Guide v3

SCP-03: Authentication

  • Password hashing: bcrypt / Argon2 (bukan MD5/SHA-1)
  • Implementasi Multi-Factor Authentication (MFA)
  • Account lockout setelah N percobaan gagal (rate limiting)
  • Password strength enforcement — panjang minimum 12 karakter
  • Hindari "remember me" tanpa token aman
  • Pesan error generik: "Email atau password salah" (jangan spesifik)
❌ MD5 (JANGAN)
$hash = md5($password);
✅ bcrypt
$hash = password_hash($password,
PASSWORD_BCRYPT, ['cost'=>12]);

SCP-04: Session Management

  • Generate session ID dengan CSPRNG (min. 128-bit entropy)
  • Cookie flags: HttpOnly, Secure, SameSite=Strict
  • Regenerate session ID setelah login (session fixation prevention)
  • Session timeout: idle max 15–30 menit, absolute max 8 jam
  • Invalidate session saat logout (server-side)
  • CSRF token: per-session atau per-request

Set-Cookie aman:
Set-Cookie: sessionid=xyz; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=1800

SCP-05: Access Control

  • Deny by default — tolak akses kecuali secara eksplisit diizinkan
  • Implementasi RBAC (Role-Based Access Control) server-side
  • Jangan hanya sembunyikan elemen UI — enforce di server
  • Validasi hak akses pada setiap request, bukan hanya saat login
  • Principle of Least Privilege — user hanya dapat resource yang dibutuhkan
  • Log semua kegagalan access control
IDOR Prevention

Selalu verifikasi bahwa resource yang diakses (/api/orders/123) memang milik user yang sedang login — bukan hanya cek autentikasi.

SCP-07: Error Handling & Logging

❌ Error Verbose (Bocorkan Info)
// Stack trace terekspos ke user Fatal: mysqli_connect(): Access denied for user 'root'@'localhost' at /var/www/html/db.php line 12
✅ Error Generik + Log Internal
// User hanya lihat pesan generik try { connectDB(); } catch (e) { logger.error(e); // log detail internal showUser("Terjadi kesalahan sistem"); }

SCP-08: Data Protection

  • Klasifikasikan data: Public, Internal, Confidential, Secret
  • Enkripsi data sensitif at-rest (database, file, backup)
  • Enkripsi data in-transit (TLS 1.2+ wajib)
  • Minimisasi data — hanya simpan yang benar-benar dibutuhkan
  • PII (Personally Identifiable Information) harus dienkripsi atau di-hash
  • Hapus data sensitif dari memori setelah tidak digunakan
SCP-09 s.d. 14

Communication Security, System Config, DB Security & File Management

Mitigasi A05 Security Misconfiguration, A06 Vulnerable Components | OWASP SCP Guide v3

SCP-09: Communication Security

  • Wajibkan TLS 1.2+ untuk semua komunikasi — nonaktifkan TLS 1.0/1.1
  • Aktifkan HSTS dengan preload dan includeSubDomains
  • Validasi sertifikat server — jangan disable certificate validation
  • CORS policy ketat — hindari Access-Control-Allow-Origin: * untuk endpoint sensitif

SCP-10: System Configuration

  • Nonaktifkan fitur, service, dan port yang tidak digunakan
  • Hapus akun, password default, dan contoh aplikasi
  • Update dependency secara rutin — pantau CVE baru
  • Jalankan aplikasi dengan akun least privilege (bukan root)
  • Pisahkan environment dev/staging/production
  • Audit konfigurasi server secara berkala

SCP-11: Database Security

  • Parameterized query / Prepared Statement — tidak ada query string concatenation
  • DB user dengan least privilege — hanya izin yang diperlukan (SELECT, INSERT, tapi bukan DROP)
  • Enkripsi koneksi database (TLS/SSL)
  • Validasi dan sanitasi semua input sebelum query
  • Stored procedure untuk operasi kompleks
  • Aktifkan audit log database untuk operasi sensitif

SCP-12: File Management

  • Validasi tipe file dengan magic bytes (bukan hanya ekstensi atau Content-Type header)
  • Simpan file upload di luar document root — tidak bisa diakses langsung via URL
  • Rename file secara acak (UUID) — attacker tidak bisa menebak lokasi
  • Nonaktifkan eksekusi skrip di direktori upload (php_flag engine off)
  • Batasi tipe file, ukuran maksimal, dan jumlah upload per user

SAST

Static Application Security Testing — Semgrep

Analisis kode sumber tanpa menjalankan aplikasi | semgrep.dev | Mendukung 30+ bahasa pemrograman

Cara Kerja Semgrep

  • Menganalisis Abstract Syntax Tree (AST) kode sumber
  • Mencocokkan pola (rules) yang mendefinisikan kode rentan
  • Output: file, baris, severity, CWE mapping, dan saran perbaikan
  • Rules tersedia dari komunitas OWASP: p/owasp-top-ten
  • Dapat dijalankan lokal, di CI/CD, atau via Semgrep AppSec Platform

Perintah Dasar Semgrep

# Install pip install semgrep # Scan dengan rules OWASP Top 10 semgrep --config=p/owasp-top-ten ./src/ # Scan dengan rules PHP security semgrep --config=p/php-security ./src/ # Output JSON untuk integrasi CI/CD semgrep --config=p/owasp-top-ten \ --json -o results.json ./src/

Contoh Output Semgrep — SQL Injection

severity: ERROR rule: php.lang.security.injection .tainted-sql-string path: src/login.php line: 8 $query = "SELECT * FROM users WHERE user='$_GET[user]'"; CWE: CWE-89 (SQL Injection) OWASP: A03:2021 Message: User-controlled data in SQL query

Contoh Custom Rule Semgrep

# rules/no-md5-password.yaml rules: - id: no-md5-password-hashing patterns: - pattern: md5(...) message: "Gunakan bcrypt/Argon2, bukan MD5" severity: ERROR languages: [php, python] metadata: cwe: CWE-916 owasp: A02:2021
Keterbatasan SAST

SAST dapat menghasilkan false positive (alarm palsu). Temuan harus diverifikasi developer sebelum diblock. Gunakan --severity=ERROR untuk hanya block temuan critical di CI/CD.

SCA & Secret Detection

Software Composition Analysis & Secret Detection

Menangani A06 Vulnerable & Outdated Components dan credential leakage di repository

Software Composition Analysis (SCA)

SCA menganalisis dependency (library/package) yang digunakan aplikasi dan membandingkannya dengan database kerentanan (NVD, OSV).

  • Tool: OWASP Dependency-Check (free, open-source)
  • Deteksi: CVE dalam library, versi yang rentan, dependency transitive
  • Output: laporan HTML/XML dengan CVSS score per dependency
# OWASP Dependency-Check (CLI) dependency-check --project "myapp" \ --scan ./vendor \ --format HTML \ --out ./reports/ # Atau via Docker docker run --rm \ -v $(pwd):/src \ owasp/dependency-check \ --scan /src --format HTML
Log4Shell — Pelajaran SCA

CVE-2021-44228 (Log4j) membuktikan pentingnya SCA: library yang tampak tidak berbahaya bisa memiliki kerentanan CVSS 10.0. SCA harus dijalankan setiap build.

Secret Detection dengan Gitleaks

Secret detection memindai repository untuk menemukan credential, API key, password, atau token yang tidak sengaja di-commit.

  • Tool: Gitleaks — open-source, cepat, mendukung pre-commit hook
  • Deteksi: AWS keys, GitHub tokens, private keys, DB passwords, JWT secrets
  • Scan seluruh git history — bukan hanya commit terbaru
# Install dan scan repo gitleaks detect --source . --verbose # Scan commit terbaru saja (CI/CD) gitleaks detect --source . \ --log-opts="HEAD~1..HEAD" # Contoh output temuan: RuleID: generic-api-key File: config/database.php Line: 12 Secret: DB_PASSWORD=p@ssw0rd123 Commit: a1b2c3d4
Pre-commit Hook

Tambahkan Gitleaks sebagai pre-commit hook agar credential tidak pernah masuk ke repository. Gunakan .gitleaks.toml untuk kustomisasi aturan dan whitelist.

DAST

Dynamic Application Security Testing — OWASP ZAP

Menguji aplikasi web yang sedang berjalan dari perspektif attacker | zaproxy.org | Open-source, gratis

Cara Kerja OWASP ZAP

  • Bertindak sebagai proxy man-in-the-middle antara browser dan aplikasi
  • Passive Scan: menganalisis traffic tanpa mengirim payload berbahaya
  • Active Scan: mengirim payload uji ke setiap parameter yang ditemukan
  • Spider: crawl otomatis semua halaman/endpoint aplikasi
  • Integrasi API: bisa dikontrol via REST API atau command line untuk CI/CD

Mode Scan ZAP

ModeDeskripsiPenggunaan
SafeTidak mengirim request berbahayaObservasi traffic
ProtectedHanya scan target yang ditentukanCI/CD testing
StandardScan normal dengan active scanPentest staging
AttackAgresif, scan cepatLab/pentest

ZAP CLI — Otomasi untuk CI/CD

# ZAP Full Scan via Docker docker run --rm -t \ ghcr.io/zaproxy/zaproxy:stable \ zap-full-scan.py \ -t http://staging.myapp.com \ -r zap-report.html # ZAP API Scan (REST/GraphQL) docker run --rm -t \ ghcr.io/zaproxy/zaproxy:stable \ zap-api-scan.py \ -t http://api.myapp.com/openapi.json \ -f openapi \ -r api-report.html

Alert Level ZAP

🔴 High — SQL Injection, RCE, Auth Bypass. Wajib diperbaiki sebelum release.
🟠 Medium — XSS, CSRF, Missing Headers. Perbaiki di sprint berikutnya.
🟡 Low — Cookie flags, path disclosure. Perbaiki jika memungkinkan.
ℹ️ Informational — Informasi saja, bukan kerentanan.
DAST vs SAST

DAST menemukan kerentanan yang hanya muncul saat runtime (logic flaws, race condition, konfigurasi server). Gunakan keduanya secara komplementer.

CI/CD Security Gate

Integrasi Security Gate ke CI/CD Pipeline

Contoh implementasi dengan GitHub Actions — mencegah merge/deploy kode yang mengandung kerentanan kritis

Prinsip Security Gate

  • Security gate memblokir pipeline jika ditemukan temuan di atas threshold tertentu
  • Threshold umum: block jika ada temuan Critical atau High
  • Medium dan Low: warning, tidak block (dilaporkan ke developer)
  • Setiap job (SAST, SCA, DAST) adalah gate tersendiri
  • Deploy hanya bisa terjadi jika semua gate lulus

Alur GitHub Actions: Setiap push/PR → trigger workflow → SAST + SCA berjalan paralel → jika lulus, DAST dijalankan → jika semua lulus, deploy ke staging.

Jangan Block Terlalu Ketat di Awal

Saat pertama kali menerapkan security gate, mulai dengan warn-only mode untuk semua temuan. Setelah tim terbiasa, tingkatkan ke block mode secara bertahap.

Contoh GitHub Actions — Security Pipeline

# .github/workflows/security.yml name: Security Pipeline on: [push, pull_request] jobs: sast: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Run Semgrep SAST uses: semgrep/semgrep-action@v1 with: config: p/owasp-top-ten generateSarif: "1" sca: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: OWASP Dependency Check uses: dependency-check/Dependency-Check_Action@main with: project: "myapp" path: "." format: "HTML" failBuildOnCVSS: "7" dast: needs: [sast, sca] runs-on: ubuntu-latest steps: - name: ZAP Full Scan uses: zaproxy/action-full-scan@v0.10.0 with: target: "http://staging.myapp.com" fail_action: "true"
Studi Kasus

Studi Kasus: Kode PHP Rentan → SAST Detection → Patch → DAST Verifikasi

End-to-end workflow DevSecOps — dari kode rentan hingga terverifikasi aman

Fase 1: Kode Rentan (login.php)

❌ Kode Rentan — Multiple Vulnerabilities
<?php // SCP-01 VIOLATION: tidak ada input validation $user = $_POST['username']; $pass = $_POST['password']; // SCP-06 VIOLATION: MD5 password hashing $hashed = md5($pass); // SCP-11 VIOLATION: SQL string concatenation $sql = "SELECT * FROM users WHERE username='$user' AND password='$hashed'"; $result = mysqli_query($conn, $sql); // SCP-07 VIOLATION: verbose error if (!$result) { die(mysqli_error($conn)); // bocorkan info DB! }

Fase 2: Semgrep Deteksi

$ semgrep --config=p/owasp-top-ten login.php ERROR login.php:10 | tainted-sql-string SQL query built from user input → SQLi risk CWE-89 | OWASP A03:2021 ERROR login.php:7 | md5-used-as-password-hash MD5 is cryptographically broken CWE-916 | OWASP A02:2021 Found 2 findings. Exit code: 1 (BLOCKED)

Fase 3: Patch (Secure Version)

✅ Kode Aman — OWASP SCP Compliant
<?php // SCP-01: Input validation (whitelist) $user = trim($_POST['username']); if (!preg_match('/^[a-zA-Z0-9_]{3,20}$/', $user)) { http_response_code(400); exit; } // SCP-06: Ambil hash dari DB dulu, verify bcrypt $stmt = $conn->prepare( "SELECT password_hash FROM users WHERE username = ?" ); $stmt->bind_param("s", $user); $stmt->execute(); $row = $stmt->get_result()->fetch_assoc(); // SCP-06: bcrypt verify (bukan MD5) if (!$row || !password_verify($pass, $row['password_hash'])) { // SCP-07: pesan generik die("Email atau password salah"); }

Fase 4: ZAP Verifikasi

$ zap-full-scan.py -t http://staging/login.php Active Scan: SQL Injection Test ... PASS Active Scan: Auth Bypass Test ... PASS Passive Scan: Cookie Flags ... PASS (HttpOnly+Secure) Alerts: 0 High, 0 Medium Report saved: zap-report.html Exit code: 0 (PASSED ✓)

Pipeline result: SAST ✓ → SCA ✓ → DAST ✓ → Deploy ke staging diizinkan.

Kuis Pertemuan 11 — Secure Coding & DevSecOps

5 soal pilihan ganda · Sub-CPMK 263.3

Soal 1 dari 5
Seorang developer menulis kode: $sql = "SELECT * FROM users WHERE id=" . $_GET['id'];. Berdasarkan OWASP Secure Coding Practices Guide, kategori SCP mana yang pertama kali harus diterapkan untuk mencegah kerentanan ini?
Benar! SCP-01 (Input Validation) adalah pertahanan pertama — tolak atau sanitasi input $_GET['id'] yang tidak valid. Selanjutnya, SCP-11 (Database Security) menambahkan prepared statement sebagai pertahanan kedua (defense-in-depth).
Kurang tepat. Kerentanan ini adalah SQL Injection (A03). OWASP SCP menempatkan Input Validation (SCP-01) sebagai pertahanan pertama — validasi bahwa id hanya berisi angka sebelum diproses. Selanjutnya gunakan prepared statement (SCP-11).
Soal 2 dari 5
Tim pengembangan ingin mengukur kematangan keamanan mereka dan menetapkan target perbaikan. Mereka saat ini sudah melakukan code review manual tapi belum ada SAST otomatis. Berdasarkan OWASP SAMM v2.0, Business Function mana yang paling relevan, dan pada Practice apa mereka seharusnya fokus?
Benar! Dalam OWASP SAMM, Business Function Verification mencakup Security Testing. Level 1 = testing ad-hoc/manual. Level 2 = pengujian otomatis terintegrasi ke CI/CD (SAST). Tim ini berada di Level 1 dan perlu naik ke Level 2 dengan mengotomasi SAST di pipeline.
Kurang tepat. OWASP SAMM memiliki 5 Business Functions. Code review manual dan SAST masuk ke Verification — Security Testing. Level 2 pada practice ini mengharuskan pengujian keamanan otomatis di pipeline CI/CD — itulah yang harus menjadi target tim.
Soal 3 dari 5
Sebuah perusahaan menemukan bahwa library Apache Log4j versi 2.14.1 yang digunakan dalam aplikasinya memiliki CVE-2021-44228 (Log4Shell) dengan CVSS 10.0. Jenis pengujian keamanan otomatis mana yang paling tepat untuk mendeteksi masalah ini secara otomatis di pipeline CI/CD?
Benar! SCA (Software Composition Analysis) dirancang khusus untuk mendeteksi kerentanan pada dependency/library — termasuk Log4j. OWASP Dependency-Check membandingkan versi library dengan NVD (National Vulnerability Database) dan akan menandai Log4j 2.14.1 sebagai rentan (CVE-2021-44228).
Kurang tepat. Kerentanan ini ada pada library (Log4j), bukan pada kode yang Anda tulis sendiri. SCA (Software Composition Analysis) adalah alat yang tepat — ia menganalisis semua dependency dan membandingkannya dengan database CVE. SAST hanya menganalisis source code Anda sendiri, bukan library.
Soal 4 dari 5
Dalam pipeline CI/CD menggunakan GitHub Actions, Semgrep (SAST) menemukan kerentanan SQL Injection (severity: ERROR) pada kode yang di-push. Apa yang seharusnya terjadi menurut prinsip DevSecOps security gate?
Benar! Security gate dengan severity ERROR/Critical harus menghentikan pipeline (exit code non-zero). Ini mencegah kode rentan masuk ke main branch atau production. Developer harus memperbaiki dan push ulang sebelum pipeline dapat lanjut — inilah inti konsep "fail fast" dalam DevSecOps.
Kurang tepat. Security gate dirancang untuk menghentikan pipeline jika ditemukan kerentanan kritis — bukan hanya melaporkan. Membiarkan pipeline lanjut sama artinya dengan tidak memiliki security gate. Prinsip DevSecOps: kode rentan tidak boleh sampai ke production.
Soal 5 dari 5
Seorang developer secara tidak sengaja meng-commit file config.php yang berisi $db_password = "admin123"; ke repository GitHub publik. Tool mana dan kapan idealnya masalah ini dapat terdeteksi sebelum sampai ke repository?
Benar! Gitleaks sebagai pre-commit hook adalah solusi terbaik — ia mendeteksi credential hardcoded sebelum commit terjadi, sehingga secret tidak pernah masuk ke git history. Ini adalah implementasi Shift Left yang paling efektif untuk secret detection. Semgrep dapat juga mendeteksi hardcoded secret, tapi pre-commit hook lebih awal.
Kurang tepat. Idealnya secret terdeteksi sebelum masuk ke repository. Gitleaks sebagai pre-commit hook menjalankan scan saat developer mengetik git commit — jika ditemukan secret, commit ditolak. Ini jauh lebih baik dari mendeteksi di CI/CD karena secret sudah masuk ke git history meski belum di-push.
