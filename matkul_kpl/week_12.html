Review Konsep Kunci dari Pertemuan 11

SAST (Static)

  • Analisis source code tanpa eksekusi
  • Temukan: hardcoded secret, SQL injection, XSS di kode
  • Tools: Semgrep, CodeQL, Bandit, SonarQube
  • Dipasang di CI pipeline (pre-commit / PR check)

DAST (Dynamic)

  • Uji aplikasi yang sedang berjalan
  • Temukan: kerentanan runtime — injection, auth bypass
  • Tools: OWASP ZAP, Burp Suite Scanner
  • Dipasang setelah aplikasi deploy ke staging

DevSecOps Pipeline

  • Shift-left: keamanan sejak awal development
  • Urutan: commit → SAST → build → DAST → deploy
  • Temuan otomatis harus ditindaklanjuti oleh developer
  • P12 = tindak lanjut manual atas temuan pipeline
Code Review

Code Review Keamanan: Konsep & Pendekatan

Mengapa review manual tetap penting meskipun ada tool otomatis?

Apa itu Security Code Review?

Security Code Review adalah proses memeriksa source code secara sistematis untuk mengidentifikasi kerentanan keamanan sebelum aplikasi dijalankan di produksi. Ini melibatkan kombinasi analisis otomatis (SAST/DAST) dan inspeksi manual oleh reviewer.

Tiga Pendekatan Utama

  • Automated SAST — tool scan kode sumber, cepat & konsisten
  • Automated DAST — tool uji runtime, temukan behaviour vulnerability
  • Manual Review — pemahaman logika bisnis, bypass tool, false negative
False Negative Problem

Tools otomatis hanya menemukan ~40–60% kerentanan yang ada. Logika bisnis yang cacat (misalnya: user A bisa akses data user B) hampir tidak bisa dideteksi tool — harus manual.

Kapan Code Review Dilakukan?

1
Pre-Commit
Semgrep / git hooks — cegah kode buruk masuk repo
2
Pull Request Review
Peer review manual + CodeQL / SonarQube CI check
3
Post-Deploy (Staging)
DAST scan ZAP/Burp — temukan kerentanan runtime
4
Remediasi & Re-Test
Perbaiki kode → scan ulang → verifikasi fix
Static Analysis (SAST)

SAST Deep Dive: Tools & Cara Membaca Temuan

Semgrep · Bandit · CodeQL · SonarQube

Open Source · Fast

Semgrep

  • Pattern-matching berbasis AST
  • Mendukung 30+ bahasa
  • Rule siap pakai: p/owasp-top-ten
  • Integrasi GitHub Actions mudah
  • Output: JSON / SARIF
Python · Open Source

Bandit

  • Khusus Python security issues
  • Deteksi: hardcoded password, SQL injection, weak crypto
  • Severity: LOW / MEDIUM / HIGH
  • Confidence: LOW / MEDIUM / HIGH
  • Cocok untuk project Django/Flask
GitHub · Enterprise

CodeQL

  • Query language atas AST kode
  • Deteksi alur data (taint tracking)
  • Temukan: injection, path traversal, SSRF
  • Terintegrasi GitHub Security Alerts
  • Sangat akurat, lebih lambat

Contoh Output Semgrep & Cara Interpretasi

FINDING [python.django.security.injection.tainted-sql-string] Severity: ERROR | Category: INJECTION | CWE-89 File: app/views.py | Line: 34 Code: query = "SELECT * FROM users WHERE id = " + user_id cursor.execute(query) Why flagged: `user_id` berasal dari request.GET (user input) dan langsung digabungkan ke SQL string — SQL Injection. Recommended fix: Gunakan parameterized query cursor.execute("SELECT * FROM users WHERE id = %s", [user_id])

True Positive: Temuan valid — user_id memang dari input tidak tervalidasi, langsung masuk SQL. Harus diperbaiki.

False Positive

Jika user_id sudah divalidasi sebagai integer sebelumnya, Semgrep tetap flagging. Reviewer wajib verifikasi manual sebelum dismiss.

Dynamic Analysis (DAST)

DAST Deep Dive: OWASP ZAP & Interpretasi Laporan

Dari scan otomatis ke tindakan remediasi yang tepat

OWASP ZAP — Cara Kerja

ZAP (Zed Attack Proxy) bertindak sebagai proxy antara browser dan server. ZAP merekam semua request/response, kemudian secara otomatis mengirim payload berbahaya untuk mendeteksi kerentanan runtime.

# ZAP Baseline Scan (Docker) docker run -t owasp/zap2docker-stable zap-baseline.py \ -t http://staging.app.local \ -r zap_report.html \ -J zap_report.json # ZAP Full Scan (lebih dalam) docker run -t owasp/zap2docker-stable zap-full-scan.py \ -t http://staging.app.local \ -r full_report.html

Review Checklist

Code Review Security Checklist

Panduan sistematis untuk reviewer — dari kriteria ke lokasi pemeriksaan

Kategori KRITIS — Periksa Pertama

!

Input Validation — Apakah semua input user divalidasi sebelum diproses? (type, length, format, whitelist)

!

Database Query — Apakah ada string concatenation langsung ke SQL? Gunakan parameterized query / ORM.

!

Output Encoding — Apakah data user di-encode sebelum ditampilkan ke HTML? (XSS prevention)

!

Authentication Check — Apakah endpoint sensitif dilindungi @login_required / middleware auth?

!

Hardcoded Secrets — Apakah ada password, API key, atau token yang di-hardcode dalam kode?

Kategori TINGGI — Periksa Berikutnya

▲

Authorization (IDOR) — Apakah akses resource divalidasi berdasarkan kepemilikan? User A tidak bisa akses data user B.

▲

File Upload — Apakah tipe file dan ukuran divalidasi? Apakah file disimpan di luar webroot?

▲

Error Handling — Apakah pesan error mengekspos informasi sensitif (stack trace, DB schema, path server)?

▲

Kriptografi — Apakah menggunakan algoritma lemah (MD5, SHA1, DES)? Password harus di-hash dengan bcrypt/argon2.

✓

Logging — Apakah event keamanan dilog (login gagal, akses ditolak)? Apakah data sensitif masuk log?

Studi Kasus 1 of 4

SQL Injection — Temuan & Remediasi

OWASP A03:2021 Injection · CWE-89 · Severity: CRITICAL

CWE-89 OWASP A03:2021 CVSS: 9.8 Critical Ditemukan via: SAST (Semgrep) + DAST (ZAP)
KODE RENTAN
# Python / Django view def get_user(request): user_id = request.GET.get('id') query = ("SELECT * FROM users " "WHERE id = " + user_id) cursor.execute(query) return cursor.fetchone() # Serangan: ?id=1 OR 1=1-- # → Dump seluruh tabel users!
Mengapa Rentan?

Input user_id langsung digabungkan ke string SQL. Attacker bisa menyisipkan SQL arbitrer untuk membaca, memodifikasi, atau menghapus data.

KODE AMAN (REMEDIASI)
# Solusi 1: Parameterized Query def get_user(request): user_id = request.GET.get('id') cursor.execute( "SELECT * FROM users WHERE id = %s", [user_id] # parameter terpisah ) return cursor.fetchone() # Solusi 2: Django ORM (Lebih Aman) user = User.objects.get(id=user_id)

Mengapa Aman? Parameter tidak pernah digabungkan ke SQL string. Database driver memastikan nilai diperlakukan sebagai data, bukan perintah SQL.

Verifikasi Fix: Setelah remediasi, jalankan ulang Semgrep (semgrep --config p/python.lang.security.audit.formatted-sql-query .) dan ZAP scan. Temuan SQLi tidak boleh muncul lagi.

Studi Kasus 2 of 4

Cross-Site Scripting (XSS) — Temuan & Remediasi

OWASP A03:2021 Injection · CWE-79 · Severity: HIGH

CWE-79 OWASP A03:2021 CVSS: 6.1 Medium–High Ditemukan via: DAST (ZAP) + Manual Review
KODE RENTAN — Reflected XSS
# Flask view — langsung render input @app.route('/search') def search(): q = request.args.get('q', '') return f"<p>Hasil untuk: {q}</p>" # Serangan: # /search?q=<script>alert(document.cookie)</script> # → Script dieksekusi di browser korban!
Dampak XSS

Attacker dapat mencuri session cookie, melakukan keylogging, redirect pengguna, atau menyebarkan malware melalui halaman web yang terpercaya.

KODE AMAN (REMEDIASI)
# Solusi 1: Escape output — markupsafe from markupsafe import escape @app.route('/search') def search(): q = request.args.get('q', '') safe_q = escape(q) return f"<p>Hasil untuk: {safe_q}</p>" # Solusi 2: Gunakan Template Engine (Jinja2) return render_template('search.html', q=q) # Jinja2 auto-escape: {{ q }} → aman

Content Security Policy (CSP) sebagai defense-in-depth: tambahkan header Content-Security-Policy: default-src 'self' untuk mencegah eksekusi script dari sumber tidak dikenal.

Reflected XSS

Payload dalam URL/form, langsung di-render. Paling umum ditemukan DAST.

Stored XSS

Payload tersimpan di DB, ditampilkan ke semua user. Dampak lebih luas — ditemukan via DAST active scan.

DOM-based XSS

Payload di-proses JavaScript client-side. DAST sulit mendeteksi — perlu manual review JS.

Studi Kasus 3 of 4

Path Traversal & IDOR — Temuan & Remediasi

CWE-22 Path Traversal · CWE-639 IDOR · Logika bisnis yang bocor

PATH TRAVERSAL — KODE RENTAN
# Endpoint download file @app.route('/download') def download(): filename = request.args.get('file') filepath = '/app/uploads/' + filename return send_file(filepath) # Serangan: # /download?file=../../etc/passwd # → Baca file sensitif di luar upload dir!
Ditemukan via SAST (Semgrep rule: path-traversal)

Konfirmasi dengan DAST: ZAP active scan mengirim payload ../ dan mendeteksi konten file sistem.

PATH TRAVERSAL — REMEDIASI
import os from werkzeug.utils import secure_filename @app.route('/download') def download(): filename = request.args.get('file') # Bersihkan filename dari traversal chars safe_name = secure_filename(filename) base_dir = os.path.abspath('/app/uploads/') filepath = os.path.join(base_dir, safe_name) # Pastikan path akhir masih di dalam base_dir if not filepath.startswith(base_dir): abort(400) return send_file(filepath)

IDOR (Insecure Direct Object Reference) — CWE-639

IDOR — KODE RENTAN
@app.route('/invoice/<int:id>') def view_invoice(id): invoice = Invoice.objects.get(id=id) return render(invoice) # Tidak cek apakah invoice milik user ini! # /invoice/1, /invoice/2, ... enumerate semua
IDOR — REMEDIASI
@app.route('/invoice/<int:id>') @login_required def view_invoice(id): invoice = Invoice.objects.get( id=id, owner=current_user # filter by owner ) if not invoice: abort(403) return render(invoice)
Studi Kasus 4 of 4

Hardcoded Secrets & Broken Authentication

CWE-798 Hardcoded Credentials · OWASP A02:2021 Broken Auth

HARDCODED SECRETS — RENTAN
# settings.py SECRET_KEY = "abc123hardcodedkey" DATABASE_PASSWORD = "admin123" AWS_ACCESS_KEY = "AKIAIOSFODNN7EXAMPLE" JWT_SECRET = "mysupersecret" # .env file yang di-commit ke Git API_TOKEN=ghp_realtoken123456789 # Ditemukan SAST: Bandit B105, Semgrep # github.com/zricethezav/gitleaks
Risiko

Secret dalam Git history tidak bisa benar-benar dihapus. Siapapun dengan akses repo dapat mengekstrak kredensial tersebut — bahkan setelah commit dihapus.

HARDCODED SECRETS — REMEDIASI
# settings.py — baca dari environment import os SECRET_KEY = os.environ.get('SECRET_KEY') DB_PASSWORD = os.environ.get('DB_PASSWORD') JWT_SECRET = os.environ.get('JWT_SECRET') # .env (jangan di-commit ke Git) echo ".env" >> .gitignore # Produksi: gunakan secret manager # AWS Secrets Manager / Vault / GitHub Secrets # Rotasi semua secret yang sudah ter-expose!

Broken Authentication — Password Hashing

HASHING LEMAH — RENTAN
# MD5 — SANGAT LEMAH import hashlib hashed = hashlib.md5(password.encode()).hexdigest() # MD5: crack dalam detik dengan rainbow table! # Plain text — paling berbahaya db.save(username=user, password=password)
HASHING AMAN — REMEDIASI
# bcrypt — DIREKOMENDASIKAN import bcrypt salt = bcrypt.gensalt(rounds=12) hashed = bcrypt.hashpw(password.encode(), salt) # Django: built-in PBKDF2 (aman) user.set_password(password) # auto-hash # Atau argon2 (winner Password Hashing Competition) from argon2 import PasswordHasher ph = PasswordHasher(); ph.hash(password)
Proses Remediasi

Secure Code Remediation Workflow

Dari temuan SAST/DAST hingga verifikasi fix yang terstruktur

1
Triage Temuan

Klasifikasi: True/False Positive, prioritas severity (CRITICAL→HIGH→MED)

2
Root Cause Analysis

Pahami mengapa rentan — bukan hanya di mana. Temukan pola serupa di kode lain.

3
Buat Fix

Implementasi perbaikan secara lokal. Tulis unit test untuk memvalidasi fix.

4
Verifikasi

Jalankan SAST ulang — temuan harus hilang. Re-test manual / ZAP scan ulang.

5
Dokumentasi

Catat: temuan, CVE/CWE, fix, bukti, risk acceptance jika tidak bisa diperbaiki.

Template Dokumentasi Remediasi

Finding Record

ID : VULN-2024-001 Judul : SQL Injection pada endpoint /search Severity : CRITICAL (CVSS 9.8) CWE : CWE-89 OWASP : A03:2021 Injection Tool : Semgrep + ZAP (confirmed) File : app/views.py:34 Status : FIXED — commit #a3f9b2c Verified : 2024-06-29 — ZAP re-scan clear

Risk Acceptance (jika tidak bisa fix)

ID : VULN-2024-007 Judul : Outdated jQuery (CVE-2019-11358) Severity : MEDIUM Alasan : Dependency legacy, butuh refactor besar Mitigasi : WAF rule diaktifkan untuk block XSS Accepted by: [Nama PL] — tanggal sign-off Review date: 2024-09-30

Prinsip Defense-in-Depth: Jika satu kontrol gagal, kontrol lain masih melindungi. Fix kode (preventif) + WAF (detective) + logging (responsive) bekerja berlapis.

Ringkasan

Ringkasan Pertemuan 12

Key takeaways & koneksi ke pertemuan berikutnya

SAST — Temukan di Kode

  • Semgrep: pattern-matching cepat, 30+ bahasa
  • Bandit: Python khusus, severity + confidence
  • CodeQL: taint tracking, akurasi tinggi
  • Output: SARIF/JSON → triage → prioritas
  • Jalankan pre-commit & di CI pipeline

DAST — Temukan saat Runtime

  • ZAP: scan otomatis aplikasi berjalan
  • Alert: Risk HIGH/MED/LOW + CWE + solution
  • Interpretasi: True Positive vs False Positive
  • Prioritas: perbaiki HIGH dulu
  • Jalankan di staging environment

Remediasi — Perbaiki dengan Tepat

  • SQLi → parameterized query / ORM
  • XSS → escape output / template engine
  • Path Traversal → secure_filename + path check
  • Secrets → environment variable / secret manager
  • Weak hash → bcrypt / argon2

Koneksi ke Pertemuan 13-14 (Secure SDLC): P12 mengajarkan cara memperbaiki kerentanan yang ditemukan. P13-14 melangkah lebih jauh: mencegah kerentanan dengan mengimplementasikan Secure SDLC secara end-to-end — termasuk validasi input, parameterized statements, enkripsi data pengguna, proteksi DDoS, dan keamanan penyimpanan data dalam satu proyek terintegrasi.
