Mitigasi A

Validasi Input — Fondasi Pertama Secure Coding

OWASP Input Validation Cheat Sheet · "Never trust user input"

Prinsip Utama

Semua data yang berasal dari luar batas kepercayaan aplikasi (form, URL parameter, header, file upload, API request) harus dianggap tidak terpercaya hingga tervalidasi.

Whitelist > Blacklist

  • Whitelist (Allow-list): tentukan pola yang diizinkan — lebih aman & prediktif
  • Blacklist (Deny-list): tentukan pola yang diblokir — mudah dilewati (bypass) attacker kreatif
Client-Side Saja Tidak Cukup

Validasi JavaScript di browser hanya untuk UX. Attacker dapat mem-bypass dengan mengirim request langsung (curl, Burp Repeater). Validasi server-side wajib.

Dimensi Validasi Input

1

Tipe data — pastikan integer benar-benar integer, bukan string

2

Panjang (length) — batasi panjang minimum/maksimum string

3

Format — gunakan regex untuk email, nomor telepon, kode pos

4

Rentang (range) — angka harus berada pada batas logis (misal usia 0-120)

5

Encoding — normalisasi Unicode untuk mencegah homograph bypass

Contoh Kode: Rentan vs Aman

TANPA VALIDASI
# Flask — tidak ada validasi sama sekali @app.route('/register', methods=['POST']) def register(): username = request.form['username'] age = request.form['age'] db.save(username=username, age=age) # age bisa string "abc", username bisa 5000 karakter
DENGAN VALIDASI (WHITELIST)
import re USERNAME_RE = re.compile(r'^[a-zA-Z0-9_]{3,20}$') @app.route('/register', methods=['POST']) def register(): username = request.form.get('username', '') if not USERNAME_RE.match(username): abort(400, "Username tidak valid") try: age = int(request.form.get('age', '')) if not (0 <= age <= 120): raise ValueError except ValueError: abort(400, "Usia tidak valid") db.save(username=username, age=age)

Rekomendasi praktis: gunakan library validasi teruji seperti WTForms, Marshmallow, atau Cerberus (Python) / Joi (Node.js) daripada menulis regex manual untuk setiap field.

Mitigasi B

Parameterized Statements — Mencegah SQL Injection

CWE-89 · OWASP A03:2021 Injection · Prepared Statement

Akar masalah SQL Injection: string concatenation menggabungkan input pengguna langsung ke perintah SQL, sehingga attacker bisa mengubah struktur/logika query. Solusi: pisahkan perintah SQL dari data menggunakan parameter placeholder — database driver menjamin data tidak pernah diperlakukan sebagai perintah.

Parameterized Query di Berbagai Driver/ORM

Python — sqlite3 / psycopg2

# RENTAN cur.execute("SELECT * FROM u " "WHERE id="+uid) # AMAN — placeholder %s / ? cur.execute( "SELECT * FROM u WHERE id=%s", [uid])

Django ORM

# RENTAN — raw() + f-string User.objects.raw( f"SELECT * FROM u WHERE id={uid}") # AMAN — ORM query builder User.objects.get(id=uid)

PHP — PDO

// RENTAN $q = "SELECT * FROM u WHERE id=".$_GET['id']; // AMAN — prepared statement $stmt = $pdo->prepare( "SELECT * FROM u WHERE id=?"); $stmt->execute([$id]);
Stored Procedure Tidak Otomatis Aman

Jika stored procedure dibangun dengan dynamic SQL (concatenation di dalam prosedur), tetap rentan SQLi. Prosedur harus juga menggunakan parameter binding secara internal.

Manfaat tambahan: parameterized query dapat memanfaatkan query plan caching pada database — selain lebih aman, seringkali juga lebih cepat untuk query berulang.

Defense in Depth

Kombinasikan parameterized query (kontrol utama) dengan validasi input (kontrol lapis kedua) dan least privilege pada akun database aplikasi (hanya berikan hak SELECT/INSERT yang diperlukan, jangan gunakan akun root/superuser).

Mitigasi C

Mengamankan Sesi Pengguna

OWASP Session Management Cheat Sheet · CWE-384 Session Fixation

Prinsip Manajemen Sesi Aman

1

Session ID acak & panjang — minimal 128-bit entropy, gunakan CSPRNG bawaan framework

2

Regenerasi session ID setelah login berhasil (cegah session fixation)

3

Cookie flags: HttpOnly (cegah akses JS/XSS), Secure (hanya HTTPS), SameSite=Strict/Lax (cegah CSRF)

4

Idle & absolute timeout — sesi tidak aktif harus otomatis expire

5

Invalidasi sesi saat logout eksplisit — hapus di server, bukan hanya di client

Implementasi — Flask Session

# app.py — konfigurasi cookie sesi aman app.config.update( SECRET_KEY=os.environ['SECRET_KEY'], SESSION_COOKIE_HTTPONLY=True, SESSION_COOKIE_SECURE=True, SESSION_COOKIE_SAMESITE='Lax', PERMANENT_SESSION_LIFETIME=timedelta(minutes=30) ) @app.route('/login', methods=['POST']) def login(): user = authenticate(request.form) if user: session.clear() # hapus sesi lama session.regenerate() # session ID baru session['user_id'] = user.id session.permanent = True return redirect('/dashboard') @app.route('/logout') def logout(): session.clear() # invalidasi di server return redirect('/login')
Session Fixation

Jika session ID tidak diregenerasi setelah login, attacker dapat "menetapkan" session ID korban sebelum login (misal via URL) lalu membajak sesi setelah korban login menggunakan ID tersebut.

Mitigasi D

Proteksi Dasar terhadap Serangan DDoS

Rate Limiting · Throttling · Resource Limits pada Lapisan Aplikasi

Volumetric

  • UDP flood, ICMP flood
  • Habiskan bandwidth jaringan
  • Mitigasi: di luar scope aplikasi — CDN/ISP/Scrubbing center

Protocol

  • SYN flood, Ping of Death
  • Eksploitasi state handshake TCP/IP
  • Mitigasi: firewall, SYN cookies di level OS/jaringan

Application Layer (L7)

  • HTTP flood, Slowloris, login brute-force
  • Meniru traffic normal — sulit dibedakan
  • Mitigasi: di sinilah kontrol pada kode aplikasi berperan

Kontrol pada Level Aplikasi

# Flask-Limiter — rate limiting per IP from flask_limiter import Limiter from flask_limiter.util import get_remote_address limiter = Limiter( app, key_func=get_remote_address, default_limits=["200 per day", "50 per hour"] ) @app.route('/login', methods=['POST']) @limiter.limit("5 per minute") # cegah brute-force def login(): ... @app.errorhandler(429) def ratelimit_handler(e): return jsonify(error="Terlalu banyak permintaan"), 429
1

Rate limiting per IP/akun pada endpoint sensitif (login, search, submit form)

2

Batasi ukuran request — max upload size, max payload JSON

3

Connection & request timeout — cegah slowloris (koneksi menggantung)

4

CAPTCHA/MFA setelah beberapa kali percobaan gagal berturut-turut

5

Reverse proxy/CDN/WAF (mis. Cloudflare, Nginx limit_req) sebagai lapis pertahanan tambahan di depan aplikasi

# nginx.conf — rate limiting di reverse proxy limit_req_zone $binary_remote_addr zone=login:10m rate=5r/m; location /login { limit_req zone=login burst=3 nodelay; }
Studi Kasus

Studi Kasus Terintegrasi — Aplikasi Login & Pencarian Sederhana

Menerapkan keempat mitigasi (A-D) sekaligus dalam satu endpoint

Tanpa Mitigasi = SQLi + Session Fixation + Brute-force Dengan Mitigasi = Validasi + Parameterized + Session Aman + Rate Limit
SEBELUM — RENTAN
@app.route('/login', methods=['POST']) def login(): u = request.form['user'] p = request.form['pass'] q = ("SELECT * FROM users WHERE " "user='"+u+"' AND pass='"+p+"'") row = db.execute(q).fetchone() if row: session['uid'] = row['id'] # tanpa regenerasi return redirect('/dashboard') return "Login gagal" # user=admin'-- bypass password! # Tidak ada rate limit → brute-force bebas # Session ID sama sebelum & sesudah login
SESUDAH — DENGAN MITIGASI A-D
USERNAME_RE = re.compile(r'^[a-zA-Z0-9_]{3,20}$') @app.route('/login', methods=['POST']) @limiter.limit("5 per minute") # (D) DDoS def login(): u = request.form.get('user', '') p = request.form.get('pass', '') if not USERNAME_RE.match(u): # (A) validasi abort(400) row = db.execute( "SELECT * FROM users WHERE user=%s", [u]).fetchone() # (B) parameterized if row and bcrypt.checkpw(p.encode(), row['hash']): session.clear(); session.regenerate() # (C) sesi session['uid'] = row['id'] return redirect('/dashboard') return "Login gagal", 401

Empat kontrol bekerja berlapis (defense-in-depth): validasi mencegah data cacat masuk, parameterized query mencegah manipulasi query, manajemen sesi mencegah pembajakan akun, rate limiting mencegah automasi serangan brute-force/DDoS pada endpoint yang sama.

Ringkasan

Ringkasan Pertemuan 13

Key takeaways & koneksi ke pertemuan berikutnya

A. Validasi Input

  • Whitelist > blacklist
  • Server-side wajib
  • Validasi tipe, panjang, format, rentang

B. Parameterized Query

  • Pisahkan perintah dari data
  • Berlaku di semua driver/ORM
  • + least privilege akun DB

C. Keamanan Sesi

  • Regenerasi ID saat login
  • HttpOnly, Secure, SameSite
  • Timeout & invalidasi logout

D. Proteksi DDoS

  • Rate limiting per IP/akun
  • Batasi ukuran & timeout request
  • WAF/CDN sebagai lapis tambahan

Koneksi ke Pertemuan 14: Setelah mengamankan input, query, sesi, dan lapisan permintaan (request layer), P14 melengkapi implementasi Secure SDLC dengan mengamankan data itu sendiri — enkripsi data (at-rest & in-transit), keamanan penyimpanan data, dan proteksi data pengguna sesuai prinsip privacy by design.

Yang Sudah Kita Kuasai (P13):
✓ Menerapkan validasi input berbasis whitelist
✓ Mengganti string concatenation dengan parameterized query
✓ Mengonfigurasi manajemen sesi yang aman
✓ Menerapkan rate limiting sebagai proteksi dasar DDoS

Tugas Sebelum P14

Lanjutkan proyek sederhana P13: pastikan keempat mitigasi (A-D) sudah berjalan dan terdokumentasi, karena P14 akan menambahkan modul enkripsi & penyimpanan data pada proyek yang sama.

Mini Quiz — Pertemuan 13

5 soal · Validasi Input, Parameterized Statements, Sesi & DDoS

Soal 1 dari 5
Mengapa pendekatan whitelist lebih direkomendasikan dibandingkan blacklist dalam validasi input?
Benar! Blacklist mencoba memblokir pola buruk yang diketahui — attacker kreatif dapat menemukan pola baru yang belum terdaftar. Whitelist lebih aman karena hanya mengizinkan pola yang sudah divalidasi.
Kurang tepat. Jawaban yang benar adalah (b). Whitelist aman karena mendefinisikan secara eksplisit apa yang diizinkan — bukan soal panjang kode, validasi tetap wajib server-side, dan whitelist bukan mekanisme enkripsi.
Soal 2 dari 5
Kode berikut: cursor.execute("SELECT * FROM u WHERE id="+uid) rentan SQL Injection. Solusi yang PALING TEPAT adalah:
Benar! Parameterized query memisahkan perintah SQL dari data — nilai uid tidak pernah diperlakukan sebagai bagian dari perintah SQL, sehingga injeksi tidak mungkin terjadi.
Jawaban yang benar adalah (b). Base64 bukan kontrol keamanan (mudah didecode), pembatasan panjang tidak mencegah injeksi, dan mengubah kolom SELECT tidak menghilangkan celah injeksi pada klausa WHERE.
Soal 3 dari 5
Untuk mencegah session fixation, langkah yang WAJIB dilakukan aplikasi tepat setelah pengguna berhasil login adalah:
Benar! Regenerasi session ID setelah login memastikan session ID lama (yang mungkin sudah diketahui attacker sebelum login) tidak lagi valid — ini mencegah session fixation.
Jawaban yang benar adalah (b). Pesan selamat datang tidak relevan dengan keamanan, menyimpan password di cookie sangat berbahaya, dan mengubah metode HTTP tidak berkaitan dengan session fixation.
Soal 4 dari 5
Cookie flag HttpOnly pada session cookie berfungsi untuk:
Benar! HttpOnly mencegah script (termasuk script hasil XSS) mengakses nilai cookie melalui document.cookie. Flag Secure yang mengharuskan HTTPS, bukan HttpOnly.
Jawaban yang benar adalah (a). Flag untuk HTTPS-only adalah Secure, HttpOnly tidak mengenkripsi cookie, dan pembatasan path diatur oleh atribut Path, bukan HttpOnly.
Soal 5 dari 5
Sebuah endpoint /login menerima ribuan percobaan login per menit dari satu alamat IP (indikasi brute-force/DDoS layer aplikasi). Mitigasi PALING TEPAT pada kode aplikasi adalah:
Benar! Rate limiting membatasi jumlah request yang diproses dari satu sumber dalam periode waktu tertentu — mitigasi langsung dan efektif pada level aplikasi terhadap brute-force dan HTTP flood.
Jawaban yang benar adalah (b). Menghapus fitur mengorbankan fungsionalitas, security through obscurity (mengganti nama endpoint) mudah ditemukan kembali, dan menonaktifkan logging justru menghilangkan visibilitas terhadap serangan.
