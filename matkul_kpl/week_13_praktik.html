Lab 1 — Validasi Input & Parameterized Statements

Menutup celah SQL Injection pada endpoint login & pencarian | Estimasi: 40 menit

🎯 Tujuan Lab 1

  • Membuktikan endpoint /login dan /search rentan SQL Injection pada versi awal
  • Menerapkan validasi input berbasis whitelist (regex) pada field username
  • Mengganti seluruh query string concatenation dengan parameterized statement
  • Memverifikasi bahwa payload SQLi tidak lagi berhasil setelah perbaikan

Langkah 1.1 — Buktikan Kerentanan SQL Injection

  • 1
    Jalankan app_vulnerable.py, buka http://localhost:5000/login
  • 2
    Pada field user, masukkan payload: admin' -- dan field password bebas isi apa saja
  • 3
    Amati bahwa login berhasil tanpa mengetahui password asli — buktikan dengan mencatat query final yang terbentuk
  • 4
    Uji juga endpoint /search?q=' UNION SELECT username,password FROM users -- dan amati hasilnya
# Query final yang terbentuk saat payload admin' -- disisipkan: SELECT * FROM users WHERE user='admin' --' AND pass='apapun' # -- mengomentari sisa query, sehingga cek password diabaikan!

Langkah 1.2 — Terapkan Validasi Input (Whitelist)

Tambahkan validasi regex untuk username sebelum diproses lebih lanjut. Field password tidak divalidasi dengan regex (agar tidak membatasi karakter password pengguna), namun tetap dibatasi panjangnya.

import re USERNAME_RE = re.compile(r'^[a-zA-Z0-9_]{3,20}$') def login(): if request.method == 'POST': u = request.form.get('user', '') p = request.form.get('pass', '') if not USERNAME_RE.match(u) or len(p) > 128: return "Input tidak valid", 400 ...

Langkah 1.3 — Ganti ke Parameterized Statement

def login(): if request.method == 'POST': u = request.form.get('user', '') p = request.form.get('pass', '') if not USERNAME_RE.match(u) or len(p) > 128: return "Input tidak valid", 400 db = get_db() # AMAN: parameterized query row = db.execute( "SELECT id, pass_hash FROM users WHERE user=?", [u] ).fetchone() if row and bcrypt.checkpw(p.encode(), row[1]): session['uid'] = row[0] return redirect('/search') return "Login gagal", 401 def search(): q = request.args.get('q', '')[:100] # batasi panjang db = get_db() # AMAN: parameterized LIKE query rows = db.execute( "SELECT * FROM products WHERE name LIKE ?", ['%'+q+'%'] ).fetchall() return str(rows)

Lab 2 — Mengamankan Sesi Pengguna

Regenerasi session ID, cookie flags, dan timeout | Estimasi: 40 menit

🎯 Tujuan Lab 2

  • Mengamati session ID menggunakan DevTools browser sebelum dan sesudah login
  • Menerapkan regenerasi session ID setelah autentikasi berhasil
  • Mengonfigurasi cookie flags: HttpOnly, Secure, SameSite
  • Menerapkan idle timeout dan invalidasi sesi saat logout

Langkah 2.1 — Amati Session Cookie via DevTools

  • 1
    Buka http://localhost:5000/login, buka DevTools (F12) → tab Application/Storage → Cookies
  • 2
    Catat nilai cookie session SEBELUM login
  • 3
    Login dengan kredensial valid, lalu catat kembali nilai cookie session SESUDAH login
  • 4
    Pada versi rentan, nilai session ID sama persis sebelum & sesudah login — ini celah session fixation

Langkah 2.2 — Konfigurasi Cookie Aman & Regenerasi Session

import os from datetime import timedelta app.secret_key = os.environ.get('SECRET_KEY', os.urandom(32)) app.config.update( SESSION_COOKIE_HTTPONLY=True, SESSION_COOKIE_SAMESITE='Lax', # SESSION_COOKIE_SECURE=True # aktifkan saat sudah pakai HTTPS PERMANENT_SESSION_LIFETIME=timedelta(minutes=15) ) @app.route('/login', methods=['GET', 'POST']) def login(): if request.method == 'POST': # ... validasi & autentikasi seperti Lab 1 ... if row and bcrypt.checkpw(p.encode(), row[1]): session.clear() # (1) hapus sesi lama sepenuhnya session['uid'] = row[0] # (2) Flask otomatis membuat session ID baru session.permanent = True # (3) berlaku idle timeout 15 menit return redirect('/search') return "Login gagal", 401 @app.route('/logout') def logout(): session.clear() # invalidasi sesi di server return redirect('/login')
Catatan Flask

Secara default, session.clear() yang diikuti penulisan ulang data ke session akan membuat Flask menerbitkan cookie session baru pada response berikutnya — ini efektif meregenerasi session ID.

Langkah 2.3 — Verifikasi Ulang dengan DevTools

  • 1
    Ulangi Langkah 2.1 pada versi yang sudah diperbaiki — pastikan session ID SEBELUM dan SESUDAH login berbeda
  • 2
    Pada kolom cookie di DevTools, periksa kolom HttpOnly dan SameSite — pastikan tercentang/terisi sesuai konfigurasi
  • 3
    Tunggu lebih dari 15 menit tanpa aktivitas (atau perkecil nilai timeout untuk pengujian cepat), lalu akses /search — pastikan sesi sudah expired

Lab 3 — Proteksi Dasar terhadap Serangan DDoS

Simulasi HTTP flood/brute-force & mitigasi rate limiting | Estimasi: 40 menit

🎯 Tujuan Lab 3

  • Mensimulasikan serangan brute-force/HTTP flood terhadap endpoint /login menggunakan Apache Bench
  • Menerapkan rate limiting dengan Flask-Limiter pada endpoint sensitif
  • Memverifikasi respons HTTP 429 saat batas rate limit terlampaui
  • Membandingkan beban server sebelum dan sesudah mitigasi diterapkan

Langkah 3.1 — Simulasikan Serangan (Sebelum Mitigasi)

Penting!

Simulasi ini hanya boleh dijalankan terhadap aplikasi lab Anda sendiri di localhost. Tidak pernah menjalankan load testing/DDoS terhadap sistem milik pihak lain tanpa izin tertulis.

# Simulasi 200 request, 20 concurrent, ke endpoint /login ab -n 200 -c 20 -p login_payload.txt -T application/x-www-form-urlencoded \ http://localhost:5000/login # login_payload.txt berisi: user=admin&pass=coba1 # Amati hasil: seluruh 200 request diproses server tanpa penolakan # → indikasi tidak ada proteksi brute-force/flood

Langkah 3.2 — Terapkan Rate Limiting dengan Flask-Limiter

from flask_limiter import Limiter from flask_limiter.util import get_remote_address limiter = Limiter( app, key_func=get_remote_address, default_limits=["200 per day", "50 per hour"] ) @app.route('/login', methods=['GET', 'POST']) @limiter.limit("5 per minute") # cegah brute-force def login(): ... @app.route('/search') @limiter.limit("30 per minute") def search(): ... @app.errorhandler(429) def ratelimit_handler(e): return {"error": "Terlalu banyak permintaan, coba lagi nanti"}, 429

Langkah 3.3 — Uji Ulang & Bandingkan

  • 1
    Restart aplikasi (app_secure.py), ulangi perintah ab dari Langkah 3.1
  • 2
    Amati bagian ringkasan output ab: cari baris "Non-2xx responses" — seharusnya muncul banyak respons non-2xx (429)
  • 3
    Uji manual: kirim 6 request login berturut-turut dalam 1 menit dengan curl, request ke-6 harus mengembalikan status 429
# Uji manual dengan curl (jalankan 6x berturut-turut) for i in {1..6}; do curl -s -o /dev/null -w "Percobaan $i: %{http_code}\n" \ -X POST -d "user=admin&pass=salah" \ http://localhost:5000/login done Percobaan 1: 401 Percobaan 2: 401 Percobaan 3: 401 Percobaan 4: 401 Percobaan 5: 401 Percobaan 6: 429 ← rate limit aktif!
