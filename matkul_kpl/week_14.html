Data Protection Lifecycle & Regulasi UU PDP

Melindungi data pada setiap tahap siklus hidupnya

Siklus Hidup Data & Kontrol Keamanan yang Relevan

Minimisasi data — hanya kumpulkan yang benar-benar diperlukan

Transmit (Kirim)

Enkripsi in-transit — TLS/HTTPS antara klien dan server

Delete (Hapus)

UU No. 27 Tahun 2022 — Pelindungan Data Pribadi (PDP)

Regulasi nasional yang mewajibkan pengendali data (termasuk pengembang aplikasi) menerapkan langkah teknis dan organisasi untuk melindungi data pribadi — sejalan dengan prinsip privacy by design.

Prinsip Kunci UU PDP

  • Persetujuan (Consent) — data dikumpulkan dengan izin eksplisit
  • Pembatasan tujuan — data hanya digunakan sesuai tujuan awal
  • Minimisasi data — kumpulkan seperlunya, simpan seperlunya
  • Hak subjek data — akses, koreksi, penghapusan data (right to erasure)
  • Kewajiban keamanan teknis — enkripsi, kontrol akses, notifikasi kebocoran

Mitigasi E

Enkripsi Data — At-Rest & In-Transit

OWASP Cryptographic Storage Cheat Sheet · AES-256-GCM · TLS 1.2+

Enkripsi In-Transit (Data Bergerak)

Melindungi data saat dikirim antara klien dan server dari eavesdropping/MitM menggunakan TLS 1.2+. Tanpa TLS, data (termasuk password saat login) dapat disadap di jaringan.

# Flask di belakang reverse proxy HTTPS (Nginx) # + wajibkan HTTPS dengan header HSTS from flask_talisman import Talisman Talisman(app, force_https=True, strict_transport_security=True, strict_transport_security_max_age=31536000)
Jangan Lupa

Setelah TLS aktif, ubah SESSION_COOKIE_SECURE=True (dari Lab P13) agar cookie sesi hanya dikirim melalui koneksi terenkripsi.

Enkripsi At-Rest (Data Tersimpan)

Melindungi data sensitif (NIK, nomor kartu, alamat) yang tersimpan di database menggunakan enkripsi simetris AES-256-GCM — memberikan kerahasiaan sekaligus integritas (authenticated encryption).

from cryptography.fernet import Fernet import os # Kunci disimpan di secret manager/env var — BUKAN di kode key = os.environ['DATA_ENC_KEY'].encode() fernet = Fernet(key) # AES-128-CBC + HMAC di balik layar # Enkripsi sebelum simpan ke database encrypted_nik = fernet.encrypt(nik.encode()) db.execute("INSERT INTO profil (nik_enc) VALUES (?)", [encrypted_nik]) # Dekripsi saat dibutuhkan (bukan saat listing massal!) nik = fernet.decrypt(row['nik_enc']).decode()
Kesalahan Umum

Jangan menyimpan kunci enkripsi di kode sumber atau database yang sama dengan data terenkripsi. Gunakan environment variable, AWS KMS/HashiCorp Vault, atau key management service terpisah.

Algoritma yang direkomendasikan: AES-256-GCM (simetris, data volume besar), RSA-2048+/ECC (asimetris, pertukaran kunci). Hindari algoritma usang: DES, RC4, MD5 sebagai enkripsi.

Mitigasi F

Keamanan Penyimpanan Data

Hashing Password · Secret Management · Kontrol Akses Berkas

Hashing Password

  • Gunakan bcrypt/argon2 — bukan MD5/SHA-1 (rentan rainbow table)
  • Salt otomatis unik per password (bawaan bcrypt)
  • Cost factor disesuaikan (bcrypt rounds=12+)
  • Password tidak pernah disimpan/di-log dalam bentuk plaintext

Secret Management

  • API key, DB password, JWT secret → environment variable
  • Produksi: gunakan Vault/AWS Secrets Manager
  • Rotasi berkala + audit akses secret
  • .env wajib masuk .gitignore

Kontrol Akses Berkas

  • File upload disimpan di luar webroot
  • Permission minimal (least privilege) — bukan 777
  • Backup database juga harus dienkripsi
  • Log aplikasi tidak boleh berisi data sensitif mentah

Contoh Kode: Hashing Password yang Benar

RENTAN — HASH LEMAH / PLAINTEXT
# Plaintext — paling berbahaya db.save(username=u, password=p) # MD5 — sangat lemah, crack dalam detik import hashlib hashed = hashlib.md5(p.encode()).hexdigest()
AMAN — BCRYPT
import bcrypt # Saat registrasi salt = bcrypt.gensalt(rounds=12) hashed = bcrypt.hashpw(p.encode(), salt) db.execute("INSERT INTO users (user, pass_hash) VALUES (?,?)", [u, hashed]) # Saat login if bcrypt.checkpw(p.encode(), row['pass_hash']): # login berhasil

Catatan Proyek P13-14: Jika Lab P13 sudah menggunakan bcrypt.checkpw() untuk login, pastikan proses registrasi/inisialisasi data pengguna juga menggunakan bcrypt.hashpw() — konsisten di kedua sisi.

Mitigasi G

Proteksi Data Pengguna — Privacy by Design

Minimisasi Data · Masking/Anonymization · Kontrol Akses PII · UU PDP

Prinsip Privacy by Design

1

Minimisasi data — kumpulkan & simpan hanya field yang benar-benar diperlukan aplikasi

2

Masking pada tampilan/log — tampilkan sebagian data sensitif saja (mis. 4 digit terakhir kartu)

3

Kontrol akses berbasis peran — hanya staf berwenang dapat melihat data lengkap PII

4

Audit trail — catat siapa mengakses data pribadi apa dan kapan

5

Hak penghapusan — sediakan mekanisme pengguna menghapus/mengekspor datanya

Implementasi Masking pada Kode

def mask_email(email): user, domain = email.split('@') return user[:2] + '***@' + domain # andi@mail.com → an***@mail.com def mask_card(card_number): return '**** **** **** ' + card_number[-4:] # 4111111111111111 → **** **** **** 1111 # Terapkan pada logging — jangan log data mentah import logging logging.info(f"User {mask_email(email)} melakukan checkout") # JANGAN: logging.info(f"User {email} pass={password}")

Uji sederhana: grep file log aplikasi untuk memastikan tidak ada NIK, password, atau nomor kartu lengkap yang tercatat.

Prinsip Least Privilege untuk Data

Terapkan kontrol akses berlapis: pengguna biasa hanya melihat datanya sendiri (mirip pencegahan IDOR di P12), staf admin melihat data ter-mask, dan hanya role tertentu (dengan audit log) yang dapat melihat data lengkap tidak ter-mask.

5 soal · Enkripsi Data, Keamanan Penyimpanan & Proteksi Data Pengguna

Soal 1 dari 5
Sebuah aplikasi menyimpan nomor kartu kredit pengguna di database agar dapat ditampilkan kembali saat transaksi berikutnya. Kontrol yang PALING TEPAT adalah:
Benar! Data yang perlu dibaca kembali (bukan sekadar diverifikasi seperti password) harus dienkripsi, bukan di-hash — dan kunci enkripsi harus dikelola terpisah dari data.
Jawaban yang benar adalah (b). Hashing bersifat satu arah (tidak bisa didekripsi) sehingga tidak cocok untuk data yang perlu ditampilkan kembali. Menyimpan plaintext atau Base64 (bukan enkripsi) sama-sama tidak aman.
Soal 2 dari 5
Mengapa password pengguna harus disimpan menggunakan bcrypt dan bukan enkripsi AES yang dapat didekripsi?
Benar! Karena aplikasi tidak pernah perlu mengetahui password asli (hanya memverifikasi kecocokan saat login), hashing satu arah dengan salt unik (bcrypt) lebih aman — bahkan jika database bocor, password asli tidak dapat direkonstruksi dengan mudah.
Jawaban yang benar adalah (b). Kecepatan bukan alasan utamanya (bcrypt justru sengaja dibuat lambat untuk menahan brute-force), AES bisa dipakai untuk teks, dan bcrypt justru menyertakan salt secara otomatis — bukan tanpa salt.
Soal 3 dari 5
Log aplikasi mencatat: "Login user=andi@mail.com pass=Rahasia123". Pelanggaran prinsip keamanan penyimpanan/proteksi data pengguna yang terjadi adalah:
Benar! Password tidak boleh pernah muncul dalam log dalam bentuk apapun, dan data pribadi seperti email sebaiknya di-mask. Log adalah salah satu sumber kebocoran data yang sering terlewat.
Jawaban yang benar adalah (b). Kelengkapan log tidak boleh mengorbankan keamanan data sensitif, format file (XML vs teks) tidak relevan dengan masalah ini, dan lokasi penyimpanan log bukan akar masalahnya.
Soal 4 dari 5
Berdasarkan prinsip UU No. 27/2022 (PDP) dan privacy by design, sebuah formulir pendaftaran akun email seharusnya:
Benar! Prinsip minimisasi data mewajibkan pengumpulan data seperlunya sesuai tujuan. Data tambahan yang tidak esensial harus bersifat opsional dengan persetujuan eksplisit.
Jawaban yang benar adalah (b). Mengumpulkan data berlebihan (over-collection), mewajibkan field tidak relevan, dan menyimpan tanpa batas waktu semuanya bertentangan dengan prinsip minimisasi data dan retensi terbatas pada UU PDP.
Soal 5 dari 5
Kunci enkripsi (encryption key) yang digunakan untuk mengenkripsi data at-rest sebaiknya disimpan di:
Benar! Prinsip dasar manajemen kunci: kunci harus terpisah dari data yang dienkripsinya. Jika database bocor tetapi kunci tersimpan aman di secret manager, data tetap terlindungi.
Jawaban yang benar adalah (c). Menyimpan kunci di tempat yang sama dengan data, di Git, atau hardcode di kode sumber semuanya membuat enkripsi menjadi tidak berarti — begitu satu sisi bocor, sisi lainnya ikut terbuka.
