Lab 1 — Enkripsi Data At-Rest

Mengenkripsi field sensitif (NIK) sebelum disimpan ke database | Estimasi: 40 menit

🎯 Tujuan Lab 1

  • Membangkitkan kunci enkripsi dan menyimpannya sebagai environment variable (bukan di kode)
  • Mengenkripsi field NIK menggunakan cryptography.fernet (AES-128-CBC + HMAC) sebelum disimpan
  • Mendekripsi data hanya saat benar-benar dibutuhkan, bukan pada listing massal
  • Memverifikasi bahwa data di database benar-benar tidak terbaca dalam bentuk plaintext

Langkah 1.1 — Bangkitkan & Simpan Kunci Enkripsi

  • 1
    Bangkitkan kunci Fernet sekali menggunakan skrip Python interaktif
  • 2
    Simpan kunci sebagai environment variable — jangan pernah menuliskannya langsung di source code
  • 3
    Tambahkan file yang menyimpan kunci ke .gitignore
# Bangkitkan kunci sekali saja python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())" gAAAAA... (contoh output kunci base64, 44 karakter) # Simpan sebagai environment variable (Linux/Mac) export DATA_ENC_KEY="<kunci_yang_dihasilkan>" # Windows PowerShell $env:DATA_ENC_KEY="<kunci_yang_dihasilkan>"

Langkah 1.2 — Terapkan Enkripsi pada Field NIK

import os from cryptography.fernet import Fernet import re fernet = Fernet(os.environ['DATA_ENC_KEY'].encode()) NIK_RE = re.compile(r'^\d{16}$') # (A) validasi format NIK 16 digit @app.route('/register', methods=['POST']) def register(): u = request.form.get('user', '') nik = request.form.get('nik', '') p = request.form.get('pass', '') if not (USERNAME_RE.match(u) and NIK_RE.match(nik)): return "Input tidak valid", 400 nik_enc = fernet.encrypt(nik.encode()) # enkripsi sebelum simpan pass_hash = bcrypt.hashpw(p.encode(), bcrypt.gensalt(rounds=12)) db = get_db() db.execute( "INSERT INTO users (user, nik_enc, pass_hash) VALUES (?,?,?)", [u, nik_enc, pass_hash]) db.commit() return "Registrasi berhasil" def get_nik_for_display(user_id): # Dekripsi HANYA saat satu record spesifik dibutuhkan row = get_db().execute( "SELECT nik_enc FROM users WHERE id=?", [user_id]).fetchone() nik = fernet.decrypt(row[0]).decode() return nik[:4] + '*'*12 # tampilkan ter-mask (lihat Lab 3)

Langkah 1.3 — Verifikasi Data Terenkripsi di Database

  • 1
    Registrasikan satu akun baru melalui form
  • 2
    Buka database langsung dengan sqlite3 users.db lalu SELECT user, nik_enc FROM users;
  • 3
    Pastikan kolom nik_enc berisi data biner/base64 acak, bukan 16 digit NIK asli

Lab 2 — Enkripsi In-Transit dengan HTTPS/TLS

Mengaktifkan HTTPS lokal dan memaksa penggunaan cookie aman | Estimasi: 30 menit

🎯 Tujuan Lab 2

  • Membuat sertifikat TLS self-signed untuk lingkungan lab lokal
  • Menjalankan Flask dengan HTTPS dan mengaktifkan header HSTS
  • Mengaktifkan SESSION_COOKIE_SECURE setelah HTTPS tersedia
  • Membandingkan trafik HTTP vs HTTPS menggunakan Wireshark/DevTools Network tab

Langkah 2.1 — Buat Sertifikat Self-Signed

# Untuk keperluan LAB LOKAL saja — bukan untuk produksi openssl req -x509 -newkey rsa:2048 -nodes \ -keyout key.pem -out cert.pem -days 30 \ -subj "/CN=localhost"

Langkah 2.2 — Jalankan Flask dengan HTTPS

from flask_talisman import Talisman Talisman(app, force_https=True, strict_transport_security=True, strict_transport_security_max_age=31536000) app.config['SESSION_COOKIE_SECURE'] = True # (C) lanjutan dari P13 if __name__ == '__main__': app.run(ssl_context=('cert.pem', 'key.pem'), port=5443)

Langkah 2.3 — Verifikasi & Bandingkan

  • 1
    Akses https://localhost:5443 — browser akan menampilkan peringatan sertifikat tidak terpercaya (wajar untuk self-signed), lanjutkan untuk keperluan lab
  • 2
    Buka DevTools → Network → periksa header response Strict-Transport-Security
  • 3
    Login, lalu periksa cookie session di DevTools → pastikan atribut Secure kini aktif
  • 4
    Coba akses versi HTTP (port 5000 tanpa TLS) — amati apakah force_https mengalihkan otomatis ke HTTPS
Pertanyaan Refleksi Lab 2

1. Apa yang dapat dilihat oleh penyerang yang menyadap trafik HTTP (tanpa TLS) saat pengguna login?
2. Mengapa header HSTS penting meskipun aplikasi sudah mengalihkan HTTP ke HTTPS?
3. Mengapa SESSION_COOKIE_SECURE tidak boleh diaktifkan sebelum HTTPS benar-benar tersedia?

Lab 3 — Keamanan Penyimpanan & Masking Data Pengguna

Audit hashing password & penerapan masking pada tampilan/log | Estimasi: 40 menit

🎯 Tujuan Lab 3

  • Mengaudit skema database untuk memastikan tidak ada kolom sensitif tersimpan plaintext
  • Menulis fungsi masking untuk email dan NIK, menerapkannya pada halaman profil dan log aplikasi
  • Menghapus/mengganti seluruh statement logging yang mencatat data sensitif mentah
  • Menguji bahwa file log tidak mengandung data pribadi lengkap

Langkah 3.1 — Audit Skema Database

  • 1
    Jalankan .schema users di SQLite untuk melihat seluruh kolom
  • 2
    Buat tabel audit sederhana: tandai setiap kolom sebagai Plaintext, Hashed, atau Encrypted

Langkah 3.2 — Implementasikan Fungsi Masking

def mask_email(email): if '@' not in email: return '***' user, domain = email.split('@', 1) return (user[:2] + '***@' + domain) if len(user) > 2 else '***@'+domain def mask_nik(nik_plain): return nik_plain[:4] + '*' * 12 # 3273010101990001 → 3273************ # Terapkan pada endpoint profil (tampilan) @app.route('/profile') @limiter.limit("30 per minute") def profile(): row = get_db().execute( "SELECT user, email, nik_enc FROM users WHERE id=?", [session['uid']]).fetchone() nik = fernet.decrypt(row[2]).decode() return { "user": row[0], "email": mask_email(row[1]), "nik": mask_nik(nik) }

Langkah 3.3 — Bersihkan Logging dari Data Sensitif

# SEBELUM — data mentah tercatat logging.info(f"Login attempt: user={u} pass={p} nik={nik}") # SESUDAH — hanya info yang diperlukan, ter-masking logging.info(f"Login attempt: user={u} email={mask_email(email)}") # password dan NIK TIDAK PERNAH dicatat dalam bentuk apapun

Langkah 3.4 — Uji Log Bersih dari Data Sensitif

# Setelah menjalankan beberapa aksi (login, registrasi, search), # periksa file log tidak mengandung pola sensitif: grep -E "pass=|nik=[0-9]{16}" app.log # Seharusnya TIDAK ADA hasil (no match)
