Mitigasi A

Autentikasi vs Otorisasi pada API

"Siapa Anda?" vs "Apa yang boleh Anda akses?"

Autentikasi (Authentication)

Proses memverifikasi identitas — memastikan klien benar-benar siapa yang diklaim.

  • API Key — token statis sederhana per klien/aplikasi
  • Basic Auth — username:password di-Base64 (harus selalu via HTTPS)
  • Token-based (JWT/OAuth2) — token dinamis dengan masa berlaku
  • Mutual TLS — sertifikat klien untuk API antar-sistem sensitif

Otorisasi (Authorization)

Proses menentukan hak akses — setelah identitas terverifikasi, apa yang boleh dilakukan?

  • Role-Based Access Control (RBAC) — akses berdasarkan peran (admin, user, guest)
  • Attribute-Based Access Control (ABAC) — akses berdasarkan atribut (kepemilikan, departemen)
  • Scope-based (OAuth2 scopes) — token membawa cakupan akses tertentu
  • Object-level check — verifikasi kepemilikan resource (cegah BOLA)
Kesalahan Paling Umum

Banyak API hanya menerapkan autentikasi (memastikan token valid) tetapi lupa otorisasi (memverifikasi apakah pemilik token berhak atas resource yang diminta). Ini adalah akar dari BOLA — API1:2023 OWASP API Security Top 10.

Mitigasi B

Token API — JWT (JSON Web Token) Deep Dive

jwt.io · RFC 7519 · Struktur, Signing, dan Verifikasi

Anatomi JWT — Tiga Bagian Dipisah Titik

HEADER
{"alg":"HS256","typ":"JWT"}

Algoritma signing & tipe token
PAYLOAD (Claims)
{"sub":"user123","role":"user","exp":1735689600}

Data klaim — TIDAK terenkripsi, hanya di-encode Base64
SIGNATURE
HMACSHA256(header.payload, secret)

Bukti integritas — mencegah token dimodifikasi
Kesalahpahaman Umum

Payload JWT hanya di-encode Base64, bukan dienkripsi — siapa pun dapat membacanya (coba decode di jwt.io). Jangan pernah menaruh data sensitif (password, NIK mentah) di dalam payload JWT.

Klaim Standar Penting

KlaimArti
subSubject — identitas pemilik token (user ID)
iatIssued At — waktu token diterbitkan
expExpiration — waktu token kedaluwarsa (WAJIB diset)
audAudience — API/layanan yang dituju token ini
issIssuer — pihak yang menerbitkan token

Implementasi — PyJWT

import jwt, datetime, os SECRET = os.environ['JWT_SECRET'] def generate_token(user_id, role): payload = { 'sub': user_id, 'role': role, 'iat': datetime.datetime.utcnow(), 'exp': datetime.datetime.utcnow() + datetime.timedelta(minutes=15) } return jwt.encode(payload, SECRET, algorithm='HS256') def verify_token(token): try: return jwt.decode(token, SECRET, algorithms=['HS256']) except jwt.ExpiredSignatureError: return None # token kedaluwarsa except jwt.InvalidTokenError: return None # tanda tangan tidak valid

HS256 vs RS256: HS256 (simetris) — satu secret untuk sign & verify, cocok untuk sistem tunggal. RS256 (asimetris) — private key untuk sign, public key untuk verify, cocok saat banyak service perlu memverifikasi token tanpa memegang kunci penandatanganan.

Mitigasi B (lanjutan)

Praktik Terbaik Pengelolaan Token API

Access Token, Refresh Token, Revocation, dan Penyimpanan Aman

1
Login

Kredensial diverifikasi, server menerbitkan access token (short-lived) + refresh token (long-lived)

2
Akses API

Client kirim access token di header Authorization: Bearer <token>

3
Token Expired

Access token kedaluwarsa (15 menit) — client gunakan refresh token untuk minta token baru

4
Refresh

Server verifikasi refresh token, terbitkan access token baru — rotasi refresh token (sekali pakai)

5
Revoke

Saat logout/kompromi, refresh token dihapus dari daftar valid di server

Mengapa Dua Jenis Token?

Access token berumur pendek (menit) untuk membatasi dampak jika bocor. Refresh token berumur panjang (hari/minggu) tetapi disimpan lebih ketat dan dapat direvokasi sewaktu-waktu di sisi server (JWT stateless tidak bisa direvokasi sebelum expired, kecuali disimpan sebagai server-side state seperti refresh token).

1

Access token: umur pendek (5-15 menit), stateless, tidak disimpan di server

2

Refresh token: umur panjang, disimpan di database server (dapat direvokasi)

3

Refresh token rotation: setiap dipakai, terbitkan refresh token baru & tandai yang lama tidak valid

Penyimpanan Token di Sisi Klien

Hindari localStorage untuk Web

Token di localStorage dapat dicuri melalui XSS (JavaScript dapat membacanya). Untuk aplikasi web, simpan access token di memori (JS variable) dan refresh token di cookie HttpOnly + Secure + SameSite.

Mobile app: simpan token di secure storage khusus platform — Keychain (iOS) atau Keystore/EncryptedSharedPreferences (Android), bukan SharedPreferences biasa.

Kerangka Referensi

OWASP API Security Top 10 (2023)

Fokus pada 5 risiko paling relevan dengan autentikasi, otorisasi & token

API1:2023

Broken Object Level Authorization (BOLA)

  • Endpoint tidak memverifikasi kepemilikan objek
  • GET /orders/5 bisa diakses user lain
  • Mitigasi: cek owner_id == current_user.id di setiap akses objek
API2:2023

Broken Authentication

  • Token lemah, tanpa expiration, algoritma "none"
  • Endpoint auth tanpa rate limiting (brute-force)
  • Mitigasi: JWT dengan exp singkat + refresh rotation + rate limit
API3:2023

Broken Object Property Level Authorization

  • Excessive Data Exposure — respons API berisi field sensitif tak perlu
  • Mass Assignment — client kirim field role:"admin" yang diterima mentah
  • Mitigasi: whitelist field response & field yang boleh diubah client
API4:2023

Unrestricted Resource Consumption

  • Tanpa rate limiting → DoS lewat API (koneksi ke P13 D)
  • Query tanpa pagination → resource exhaustion
  • Mitigasi: rate limit per token/IP, batasi ukuran payload & page size
API5:2023

Broken Function Level Authorization (BFLA)

  • User biasa dapat memanggil endpoint admin karena tidak dicek role
  • Contoh: DELETE /admin/users/3 berhasil tanpa cek role
  • Mitigasi: middleware pengecekan role di setiap endpoint sensitif

Mitigasi C

Metodologi Pengujian Keamanan API

Postman · Burp Suite · OWASP ZAP API Scan

Kategori Uji Wajib

1

Uji BOLA: login sebagai User A, coba akses resource milik User B via ID

2

Uji Token Tampering: ubah payload JWT (mis. role user→admin) tanpa signature valid

3

Uji Expired Token: gunakan token kedaluwarsa, pastikan ditolak (401)

4

Uji BFLA: panggil endpoint admin menggunakan token role user biasa

5

Uji Rate Limiting: kirim request beruntun, pastikan muncul HTTP 429

6

Uji Excessive Data Exposure: periksa response JSON tidak membocorkan field internal (pass_hash, dsb)

Contoh Uji Token Tampering (Manual)

# Token asli (role: user) eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyMSIsInJvbGUiOiJ1c2VyIn0.XXXX # Decode payload, ubah "role":"user" → "role":"admin" # lalu re-encode Base64 TANPA menandatangani ulang (signature lama) curl -H "Authorization: Bearer <token_dimodifikasi>" \ http://localhost:5000/api/admin/users HTTP/1.1 401 Unauthorized {"error": "Invalid token signature"} # Hasil yang DIHARAPKAN: ditolak karena signature tidak cocok
Jika Tidak Ditolak

Jika API menerima token yang dimodifikasi, kemungkinan verifikasi signature tidak dijalankan dengan benar, atau API menerima algoritma "alg":"none" — celah kritis yang harus segera diperbaiki.

Studi Kasus

Studi Kasus Terintegrasi — REST API "Orders" Sederhana

Menerapkan JWT + otorisasi objek pada endpoint /api/orders/<id>

Sebelum: BOLA — user lain bisa lihat order siapa saja Sesudah: JWT + cek kepemilikan + rate limit
SEBELUM — RENTAN (BOLA + Broken Auth)
@app.route('/api/orders/<int:order_id>') def get_order(order_id): # Hanya cek header Authorization ada isinya, tidak diverifikasi! if not request.headers.get('Authorization'): abort(401) order = db.execute( "SELECT * FROM orders WHERE id=?", [order_id] ).fetchone() # Tidak cek apakah order ini milik pemegang token! return jsonify(dict(order)) # /api/orders/1, /api/orders/2, ... bisa dilihat siapa saja
SESUDAH — JWT + OTORISASI OBJEK
def require_auth(f): def wrapper(*args, **kwargs): token = request.headers.get('Authorization', '').replace('Bearer ','') payload = verify_token(token) # (B) verifikasi JWT if not payload: return jsonify(error="Invalid token"), 401 request.user = payload return f(*args, **kwargs) return wrapper @app.route('/api/orders/<int:order_id>') @require_auth @limiter.limit("60 per minute") def get_order(order_id): order = db.execute( "SELECT * FROM orders WHERE id=? AND owner_id=?", [order_id, request.user['sub']] # (A) cek kepemilikan ).fetchone() if not order: return jsonify(error="Not found"), 404 # bukan 403 (hindari leak) return jsonify(dict(order))

Detail penting: jika order tidak ditemukan ATAU bukan milik user, respons tetap 404 Not Found yang sama — ini mencegah attacker membedakan "order tidak ada" dari "order ada tapi bukan milik saya" (mencegah enumerasi ID).

5 soal · Autentikasi, Otorisasi, Token API & Pengujian Keamanan API

Soal 1 dari 5
Endpoint GET /api/invoices/{id} memverifikasi token JWT valid, tetapi tidak memeriksa apakah invoice tersebut milik pemegang token. Kerentanan yang terjadi adalah:
Benar! Token valid (autentikasi berhasil), tetapi API gagal memverifikasi apakah pemegang token berhak atas invoice tersebut (otorisasi objek) — ini persis definisi BOLA, API1:2023.
Jawaban yang benar adalah (b) BOLA. Soal menyebutkan token diverifikasi valid, jadi bukan Broken Authentication. Tidak ada indikasi soal rate limiting atau SQL Injection di sini.
Soal 2 dari 5
Mengapa data sensitif (seperti password atau NIK mentah) TIDAK boleh dimasukkan ke dalam payload JWT?
Benar! Base64 bukan enkripsi — siapa pun dapat men-decode payload JWT dan membaca isinya. Signature hanya menjamin integritas (tidak diubah), bukan kerahasiaan.
Jawaban yang benar adalah (b). Tidak ada batas ukuran ketat 100 karakter, JWT mendukung berbagai tipe data JSON, dan payload tidak otomatis terhapus — masalah utamanya adalah keterbacaan Base64.
Soal 3 dari 5
Seorang penguji memodifikasi klaim "role":"user" menjadi "role":"admin" pada payload JWT tanpa menandatangani ulang, lalu mengirimkannya ke API. Perilaku API yang BENAR adalah:
Benar! Modifikasi payload tanpa menandatangani ulang akan membuat signature tidak cocok. Server yang memverifikasi signature dengan benar akan menolak token ini — jika diterima, ini adalah kerentanan serius (Broken Authentication).
Jawaban yang benar adalah (b). API yang aman WAJIB menolak token dengan signature tidak valid, apa pun isi payloadnya — bukan menerimanya dengan pembatasan atau meminta login ulang.
Soal 4 dari 5
Mengapa disarankan menggunakan kombinasi access token berumur pendek + refresh token berumur panjang, dibandingkan satu token yang berumur panjang saja?
Benar! Prinsip "blast radius" — access token berumur pendek meminimalkan jendela waktu penyalahgunaan jika bocor, sementara refresh token yang jarang dikirim dan disimpan lebih aman menjadi mekanisme kontrol tambahan (dapat direvokasi di server).
Jawaban yang benar adalah (b). Ini bukan soal performa CPU, dukungan browser, atau ukuran file — melainkan strategi keamanan untuk membatasi dampak kebocoran token.
Soal 5 dari 5
Saat menguji API dengan mengakses /api/orders/999 milik user lain menggunakan token milik diri sendiri, respons yang PALING TEPAT dari sisi keamanan adalah:
Benar! Mengembalikan 404 yang identik baik untuk "resource tidak ada" maupun "resource ada tapi bukan milik Anda" mencegah attacker membedakan keduanya — teknik ini mengurangi risiko enumerasi ID yang valid.
Jawaban yang benar adalah (c). 200 OK jelas merupakan kerentanan BOLA. 403 Forbidden, meski menolak akses, membocorkan informasi bahwa order tersebut memang ada — lebih baik disamarkan menjadi 404.
