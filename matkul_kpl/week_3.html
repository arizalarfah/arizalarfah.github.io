✍️ (a) Secure Code Writing

Menulis kode yang aman sejak awal — shift-left security

✍️
Indikator a · Bloom C3

Secure Code Writing

Kode yang aman bukan sekadar kode yang berjalan — melainkan kode yang menangani input berbahaya, melindungi output, dan gagal dengan aman.

🔒 Input Validation

Validasi semua data yang masuk ke aplikasi — jangan pernah percaya input pengguna.

// ❌ BURUK — SQL Injection risk query = "SELECT * FROM users WHERE id=" + id; // ✅ BAIK — Parameterized Query query = "SELECT * FROM users WHERE id=?"; db.execute(query, [id]);
Whitelist Type Check Length Limit Regex

🔐 Output Encoding

Encode output sesuai konteks untuk mencegah XSS dan injection.

// ❌ BURUK — Reflected XSS resp.write("Halo " + user.name); // ✅ BAIK — HTML Entity Encode resp.write("Halo " + htmlEncode(user.name));
HTML Encode JS Encode URL Encode

⚠️ Error Handling & Logging

Jangan bocorkan detail error ke pengguna — log secara aman di server.

// ❌ BURUK — Stack trace ke user catch(e) { response.send(e.stack); } // ✅ BAIK — Generic error + secure log catch(e) { logger.error(e.stack); // server-side response.send("Terjadi kesalahan"); }

📋 OWASP Secure Coding Practices

  • Gunakan prepared statements untuk semua query DB
  • Terapkan allowlist bukan blocklist untuk validasi
  • Hindari fungsi berbahaya: eval(), exec(), gets()
  • Batasi ukuran buffer — cegah overflow
  • Fail securely — jika error, default ke deny
  • Terapkan Content Security Policy (CSP)
Referensi

OWASP Input Validation Cheat Sheet · CWE-89 · CWE-79 · CWE-119

🔑 (b) Secure Secret Management

Mengelola kredensial, API key, dan password dengan aman

⚠️ Risiko Nyata

Pada 2024, lebih dari 12 juta API key dan token ditemukan terbuka di GitHub publik (GitGuardian State of Secrets Sprawl). Hardcoded credentials adalah penyebab utama kebocoran data.

❌ Antipattern — Jangan Lakukan!

// SANGAT BURUK — Hardcoded secret DB_PASS = "P@ssw0rd123" API_KEY = "sk-abc123xyz..." JWT_SECRET = "mysecret" // Commit ke Git = Kebocoran permanen!

✅ Praktik Terbaik

# Gunakan environment variable DB_PASS = os.environ['DB_PASS'] API_KEY = os.environ['API_KEY'] # .env hanya untuk lokal, jangan di-commit! # Tambahkan .env ke .gitignore
Env Variables Secrets Manager Vault

📋 Secret Hygiene Checklist

  • ✅ Tambahkan .env, *.key, *.pem ke .gitignore
  • ✅ Gunakan git-secrets atau truffleHog sebagai pre-commit hook
  • ✅ Rotasi semua secret secara berkala (≤ 90 hari)
  • ✅ Gunakan short-lived tokens (OAuth, JWT exp pendek)
  • ✅ Audit akses secret — siapa, kapan, dari mana
  • ✅ Revoke segera jika secret terekspos

  • Logika otentikasi dan otorisasi

  • Penggunaan kriptografi (jangan buat sendiri!)

🚚 (d) Secure Delivery

Mengamankan pipeline CI/CD dan rantai pasokan software

A03:2025 — Software Supply Chain Failures (kategori BARU di OWASP 2025) mencakup serangan pada pipeline build, ketergantungan yang dikompromikan, dan artifact yang dimodifikasi. Contoh: SolarWinds attack (2020) — build server dikompromikan untuk menyisipkan malware.

🔒 Secure CI/CD Pipeline

📝
Source

Signed commits, branch protection, MFA required

🔬
Build

Isolated env, SAST, SCA, reproducible builds

🧪
Test

DAST, unit test, integration test, fuzz

✍️
Sign

Artifact signing (Sigstore/cosign), SBOM gen

🚀
Deploy

Verify signature, immutable infra, audit log

📐 SLSA Framework (Supply-chain Levels for Software Artifacts)

Framework Google untuk meningkatkan kepercayaan rantai pasokan software secara bertahap:

Level Requirement
SLSA 1 Dokumentasi build process, provenance generated
SLSA 2 Hosted build service, signed provenance
SLSA 3 Hardened build platform, non-falsifiable provenance
SLSA 4 Two-person review, hermetic builds, reproducible

🛡️ Praktik Secure Delivery

  • Gunakan immutable artifact registry (tidak bisa di-overwrite)
  • Tanda tangani semua artifact dengan cosign/Sigstore
  • Generate dan validasi SBOM (Software Bill of Materials)
  • Batasi akses CI/CD — prinsip least privilege
  • Audit semua perubahan pipeline configuration
  • Gunakan ephemeral build environments (destroy setelah build)
⚠️ Jangan Lakukan

Jangan pernah mengizinkan script dari PR eksternal langsung dieksekusi di CI/CD tanpa review — ini vektor serangan supply chain klasik!

📋 SBOM — Software Bill of Materials

SBOM adalah daftar inventaris lengkap semua komponen software: library, versi, lisensi, dan ketergantungan transitif.

Format Standar SBOM:
  • SPDX (ISO/IEC 5962:2021) — Linux Foundation
  • CycloneDX — OWASP Foundation
Cara Generate SBOM:
# syft — generate SBOM dari image/dir syft myapp:latest -o cyclonedx-json # grype — scan SBOM untuk CVE grype sbom:sbom.json

🔒 (f) Privacy & Privilege

Least privilege, RBAC, data minimization, dan UU PDP

🎯 Prinsip Least Privilege

Setiap komponen, user, atau proses hanya memiliki hak akses minimum yang diperlukan untuk tugasnya.

✅ Terapkan

  • DB user aplikasi hanya READ+WRITE, bukan ADMIN
  • Service account hanya akses resource yang diperlukan
  • Token API dengan scope spesifik (bukan wildcard)
  • Rotate credential secara berkala

👥 RBAC — Role-Based Access Control

Kelola hak akses berdasarkan peran, bukan individu:

Role Akses
Admin Full control, audit log access
Developer Read/write code, staging env only
Analyst Read-only data (anonymized)
App Service Specific API endpoints only

🇮🇩 UU PDP No. 27/2022 — Implikasi Teknis

Undang-Undang Perlindungan Data Pribadi mengatur kewajiban teknis bagi pengembang:

  • Data Minimization — hanya kumpulkan data yang diperlukan
  • Purpose Limitation — data hanya untuk tujuan yang dinyatakan
  • Storage Limitation — hapus data setelah tidak diperlukan
  • Breach Notification — laporkan dalam 14 hari ke BSSN & subjek data
  • Right to Erasure — implementasikan mekanisme hapus data
⚠️ Sanksi Pidana

Pelanggaran UU PDP dapat dikenai pidana penjara maksimal 6 tahun dan/atau denda Rp 6 miliar.

🔏 Data Protection Techniques

Enkripsi at-rest (AES-256) Enkripsi in-transit (TLS 1.3) Tokenisasi Pseudonymization Anonymization Data Masking Field-level Encryption
Privacy by Design

Integrasikan privasi sejak fase desain — bukan sebagai tambahan di akhir. Terapkan Privacy Impact Assessment (PIA) untuk fitur yang memproses data sensitif.

⏱️ TOTP vs FIDO2/WebAuthn

Aspek TOTP FIDO2/WebAuthn
Phishing-resistant ❌ ✅
Kebutuhan device Smartphone Platform auth / HW key
UX Mudah Sangat mudah
Implementasi TOTP library WebAuthn API
Standar RFC 6238 FIDO Alliance / W3C

📌 Rekomendasi Implementasi MFA

  • Wajibkan MFA untuk semua akun admin dan privileged
  • Gunakan FIDO2/WebAuthn (passkey) sebagai default terbaik
  • Hindari SMS OTP sebagai satu-satunya pilihan — rentan SIM-swap
  • Sediakan recovery code cadangan (simpan offline)
  • Log semua event MFA (success & failure)
  • Nonaktifkan MFA bypass yang tidak diperlukan
⚠️ SMS OTP

SMS OTP rentan terhadap serangan SIM-swapping dan SS7 interception. NIST SP 800-63B sudah mengategorikannya sebagai RESTRICTED authenticator.

📰 Studi Kasus — Insiden Nyata & Mitigasinya

Analisis kasus riil untuk memahami dampak & solusi mitigasi

💥 Kasus: Kebocoran Data Nasabah Bank (Simulasi)

Aplikasi mobile banking — 2.3 juta data nasabah terekspos akibat kombinasi kelemahan teknis

🔍 Temuan Insiden

  • API key AWS tertanam dalam source code mobile app yang dipublikasikan ke Play Store
  • No input validation pada endpoint transfer — SQL injection berhasil dieksekusi
  • Session token tidak expire — valid 30 hari tanpa MFA
  • Dependency log4j v2.14 yang rentan (Log4Shell) belum dipatch 3 bulan setelah CVE rilis
  • Error message menampilkan detail database stack trace

🛡️ Mitigasi yang Diperlukan

  • (b) Secure Secret — Hapus API key dari kode, gunakan AWS Secrets Manager, revoke key lama
  • (a) Secure Code Writing — Implementasikan parameterized query, validasi input, generic error
  • (g) MFA — Wajibkan TOTP untuk semua transaksi, session expire 15 menit
  • (e) Update — Patch log4j segera (SLA critical ≤ 24 jam), aktifkan Dependabot
  • (c) Secure Source Code — Tambahkan SAST ke CI/CD, secret scanning (truffleHog)

📊 Pemetaan ke OWASP 2025

Temuan OWASP 2025 CWE
Hardcoded API Key A02 Misconfig CWE-798
SQL Injection A05 Injection CWE-89
Tidak ada MFA A07 Auth Fail CWE-308
Log4j unpatched A03 Supply Chain CVE-2021-44228

⚖️ Dampak Regulasi

  • UU PDP — Wajib notifikasi ke BSSN + subjek data dalam 14 hari
  • OJK POJK 11/2022 — Kewajiban pelaporan insiden siber ke OJK
  • Potensi denda administratif + pidana jika terbukti lalai
  • Reputasi — kehilangan kepercayaan nasabah
  • BSSN dapat memanggil untuk audit keamanan forensik

🔑 Poin Kunci yang Harus Diingat

✓
Mitigasi bukan opsi — ini kewajiban teknis dan legal (UU PDP, PP 71/2019, BSSN)
✓
Shift-left security: temukan kerentanan sedini mungkin dalam SDLC — biaya fix di fase requirement 100× lebih murah dari production
✓
Gunakan tools otomatis (SAST, SCA, secret scanner) sebagai safety net — bukan pengganti berpikir kritis
✓
Hardcoded credentials dan unpatched dependency adalah dua penyebab terbesar kebocoran data saat ini (GitGuardian & Veracode Report 2024)
✓
MFA dengan FIDO2/WebAuthn adalah mitigasi paling efektif untuk phishing-based account takeover

🔑 Tugas 2 — Secret Management Lab (Kelompok 2 orang)

Lakukan praktikum secret management:

  • Setup aplikasi demo dengan hardcoded credentials (sengaja)
  • Jalankan truffleHog atau git-secrets — dokumentasikan temuannya
  • Migrasi ke environment variable atau HashiCorp Vault (pilih salah satu)
  • Screenshot dan laporan singkat perbandingan sebelum & sesudah
Bobot: 35% Format: Laporan + source code Sub-CPMK: 261.2b

📱 Tugas 3 — Desain MFA untuk Aplikasi (Individu)

Rancang implementasi MFA untuk sistem informasi akademik (SIAKAD):

  • Pilih 2 jenis MFA yang akan diimplementasikan — justifikasi pilihan
  • Buat flow diagram autentikasi lengkap (bisa menggunakan draw.io / Mermaid)
  • Analisis tradeoff UX vs keamanan untuk setiap pilihan
  • Identifikasi attack vector yang dapat dimitigasi dan yang tidak
