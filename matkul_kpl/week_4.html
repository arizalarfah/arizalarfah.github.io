Metode 1 — SAST

🔎 Static Application Security Testing (SAST)

Analisis kode sumber, bytecode, atau biner tanpa menjalankan aplikasi

📌 Konsep SAST

SAST menganalisis kode secara statis — seperti "spell checker" untuk keamanan. Dilakukan tanpa menjalankan aplikasi, sehingga bisa diintegrasikan langsung ke IDE atau pipeline CI/CD.

White Box Testing Butuh Source Code Shift-Left Security

Apa yang dicari SAST? SQL Injection, XSS, buffer overflow, hardcoded secrets, insecure crypto, race condition, path traversal, dan 100+ pola CWE lainnya.

✅ Kelebihan SAST

  • Menemukan kerentanan sangat dini — sebelum kode di-deploy
  • Coverage tinggi — dapat memindai seluruh codebase
  • Dapat diautomasi dalam pipeline CI/CD
  • Tidak memerlukan aplikasi yang sedang berjalan
  • Murah: biaya perbaikan jauh lebih rendah

⚠️ Keterbatasan SAST

  • False positive tinggi — perlu triase manual
  • Tidak dapat mendeteksi kerentanan yang muncul saat runtime (misal: race condition di environment tertentu)
  • Kurang efektif untuk logika bisnis yang kompleks
  • Membutuhkan akses ke source code (tidak cocok untuk third-party binary)

Metode 2 — DAST

🌐 Dynamic Application Security Testing (DAST)

Pengujian aplikasi yang sedang berjalan — mensimulasikan serangan dari perspektif eksternal

📌 Konsep DAST

DAST bekerja seperti "robot attacker" yang mengirim request ke aplikasi yang berjalan dan menganalisis respons untuk menemukan kerentanan. Tidak memerlukan akses ke source code.

Black Box Testing Butuh Aplikasi Running Perspektif Attacker

Apa yang ditemukan DAST? XSS, SQLi, CSRF, insecure headers, open redirects, exposed sensitive data, misconfigurations, dan kerentanan authentication/authorization.

✅ Kelebihan DAST

  • Tidak perlu source code → cocok untuk third-party app
  • Menemukan kerentanan runtime yang tidak terlihat oleh SAST
  • False positive lebih rendah — kerentanan benar-benar dapat dieksploitasi
  • Dapat memvalidasi perbaikan yang sudah dilakukan

⚠️ Keterbatasan DAST

  • Coverage terbatas — hanya menguji endpoint yang dapat dijangkau
  • Bisa merusak data di database (harus gunakan environment uji)
  • Lambat — memindai semua endpoint membutuhkan waktu
  • Tidak dapat melihat logika internal kode

🛠️ Tools DAST yang Dipelajari

🔑 SAST + DAST = Pendekatan Lengkap

SAST menemukan kerentanan di dalam kode. DAST menemukan kerentanan yang terlihat dari luar. Keduanya saling melengkapi — gunakan keduanya untuk coverage optimal.

Metode 3 & 4

🎯 Penetration Testing & Fuzz Testing

Dua metode lanjutan: simulasi serangan terstruktur dan pengujian berbasis input acak

🎯 Penetration Testing (Pentest)

Simulasi serangan nyata oleh tim security profesional dengan tujuan menemukan kerentanan yang dapat dieksploitasi, sebelum attacker sesungguhnya melakukannya.

Metodologi Standar (PTES / OWASP Testing Guide):
1
Scoping

Definisikan target & aturan main

2
Recon

Kumpulkan informasi target

3
Scanning

Identifikasi kerentanan aktif

4
Exploit

Buktikan kerentanan dapat dieksploitasi

5
Report

Laporan temuan & rekomendasi

⚠️ Etika & Legalitas

Penetration testing wajib dilakukan dengan izin tertulis (Rules of Engagement). Tanpa izin, tindakan ini melanggar hukum (UU ITE Pasal 30). Di kelas ini, semua pentest dilakukan di lab tertutup.

🎲 Fuzz Testing (Fuzzing)

Teknik mengirimkan input acak, tidak valid, atau tidak terduga ke aplikasi untuk menemukan crash, memory leak, atau perilaku tak terduga yang bisa dieksploitasi.

✅ Input Normal

  • username: "john"
  • age: 25
  • email: "a@b.com"

🎲 Input Fuzzer

  • "\x00\xff\xfe..."
  • -2147483649
  • "A"×100000
  • null, undefined
  • %00%0d%0a...

🛠️ Tools Fuzzing

Burp IntruderHTTP/APIDictionary & brute-force attack

Kapan gunakan Fuzzing? Setelah pengujian fungsional selesai, sebelum release, dan untuk input parser / protokol kustom yang sering jadi titik lemah tersembunyi.

Analisis Hasil — Indikator 2

📊 Menginterpretasikan Hasil Pengujian Kerawanan

Memahami alert, severity, CVSS score, dan cara memprioritaskan temuan

📋 Komponen Alert ZAP/Burp

Setiap temuan tools DAST biasanya berisi:

KomponenPenjelasan
Alert NameNama kerentanan (misal: SQL Injection)
Risk/SeverityHigh / Medium / Low / Informational
ConfidenceHigh / Medium / Low (keyakinan tools)
URL AffectedEndpoint yang rentan
ParameterParameter yang dieksploitasi

SolutionRekomendasi perbaikan dari OWASP

🎯 CVSS Score — Prioritas Penanganan

Common Vulnerability Scoring System v3.1 — skala 0–10:

9.0–10.0
CRITICAL — Tangani dalam 24 jam. Dapat dieksploitasi secara remote tanpa autentikasi.
7.0–8.9
HIGH — Tangani dalam seminggu. Dampak signifikan terhadap konfidensialitas/integritas/ketersediaan.
4.0–6.9
MEDIUM — Tangani dalam sebulan. Memerlukan kondisi tertentu untuk dieksploitasi.
0.1–3.9
LOW — Rencanakan perbaikan di sprint/iterasi berikutnya.
💡 Tips Triase Hasil Scan
  • Prioritaskan High Confidence + High Risk terlebih dahulu
  • Low Confidence = verifikasi manual sebelum melaporkan
  • Kelompokkan temuan serupa agar laporan lebih ringkas
  • Selalu sertakan bukti (evidence) dan langkah reproduksi
Studi Kasus Praktikum

🔬 Studi Kasus: Pengujian DVWA menggunakan OWASP ZAP

Simulasi alur pengujian lengkap pada aplikasi lab yang sengaja dibuat rentan

🎯 Skenario: Tim Security Engineer PSSN

Anda diminta melakukan security assessment terhadap aplikasi web internal sebelum go-live. Gunakan OWASP ZAP untuk melakukan scanning dan dokumentasikan hasil pengujian.

Fase 1: Persiapan & Scoping

  • Setup DVWA di Docker: docker run -d -p 80:80 vulnerables/web-dvwa
  • Set DVWA security level ke "Low" di setup.php
  • Konfigurasi ZAP proxy di browser (localhost:8080)
  • Definisikan scope: http://localhost/dvwa/
  • Catat autentikasi yang diperlukan (admin/password)

Fase 2: Spider & Reconnaissance

  • Login ke DVWA melalui browser (ZAP merekam session)
  • Di ZAP → klik kanan URL → Attack → Spider
  • ZAP crawl semua halaman DVWA yang dapat dijangkau
  • Periksa Sites panel — semua endpoint terdaftar
  • Pastikan halaman sensitif (SQLi, XSS, Upload) teridentifikasi

Fase 3: Active Scanning

  • Klik kanan URL → Attack → Active Scan
  • Pilih semua scan policy (OWASP Top 10)
  • Tunggu hingga scan selesai (5–15 menit)
  • Monitor Alerts yang muncul secara real-time
  • Catat setiap alert: nama, severity, URL, parameter

Fase 4: Dokumentasi & Laporan

  • Review semua alert → filter High & Medium
  • Verifikasi manual setiap High Confidence alert
  • Generate Report: Report → Generate Report → HTML
  • Isi template laporan: temuan, severity, bukti, rekomendasi
  • Presentasikan ke dosen dengan format penetration testing mini
💡 Catatan Penting

Semua kegiatan pengujian hanya pada DVWA lokal. DVWA adalah aplikasi yang sengaja dibuat rentan untuk tujuan pendidikan — penggunaannya di environment produksi dilarang keras.

📊 Hasil yang Diharapkan: ZAP biasanya menemukan 15–25 alert di DVWA level Low, mencakup SQLi, XSS Reflected/Stored, Command Injection, Path Traversal, dan berbagai misconfigurations.

Kerentanan 1 – Port 21

FTP – VSFTPD 2.3.4 Backdoor

Versi VSFTPD 2.3.4 mengandung backdoor yang sengaja ditanam – memungkinkan Remote Command Execution

📋 Profil Kerentanan

Service / ProtocolFTP (File Transfer Protocol)
Nama ProgramVSFTPD (Very Secure FTP Daemon)
Versi2.3.4
Jenis KerentananBackdoor Command Execution
Referensi Exploit-DBhttps://www.exploit-db.com/exploits/17491
Modul Metasploitexploit/unix/ftp/vsftpd_234_backdoor

Penjelasan Kerentanan

Versi VSFTPD 2.3.4 yang didistribusikan antara Juni–Juli 2011 mengandung backdoor yang ditanam oleh pihak tidak bertanggung jawab pada server distribusi resmi. Backdoor ini dipicu ketika username FTP mengandung karakter ":)". Ketika dipicu, server membuka port 6200 dan memberikan akses shell dengan hak akses root.

Identifikasi dengan Searchsploit

Terminal – Kali Linux
$ searchsploit vsftpd 2.3.4
---------------------------------------------------------------------- Exploit Title | Path ---------------------------------------------------------------------- vsftpd 2.3.4 - Backdoor Command Execution | unix/remote/17491.rb ----------------------------------------------------------------------

Evaluasi

🎯 Kuis Interaktif — Pertemuan 4

Uji pemahaman tentang jenis pengujian dan perangkat uji kerawanan

Soal 1 dari 5
Seorang developer ingin menemukan kerentanan SQL Injection di kode Python sebelum aplikasi dijalankan. Metode pengujian yang paling tepat adalah…
✅ Benar! SAST menganalisis source code tanpa menjalankan aplikasi. Ini adalah metode yang tepat untuk deteksi dini kerentanan di fase coding, sebelum aplikasi di-deploy.
❌ Kurang tepat. DAST dan Pentest memerlukan aplikasi yang berjalan. Fuzz Testing mengirim input acak ke runtime. SAST adalah satu-satunya yang dapat menganalisis kode sebelum dieksekusi.
Soal 2 dari 5
Perbedaan utama antara OWASP ZAP dan Semgrep adalah…
✅ Benar! OWASP ZAP adalah DAST tool (web proxy + scanner yang bekerja saat aplikasi berjalan), sedangkan Semgrep adalah SAST tool (menganalisis source code secara statis).
❌ Kurang tepat. Keduanya open source dan gratis. OWASP ZAP = DAST (menguji aplikasi yang sedang berjalan dari luar), Semgrep = SAST (menganalisis source code tanpa eksekusi).
Soal 3 dari 5
Sebuah alert di OWASP ZAP menunjukkan Risk: High, Confidence: Low. Apa tindakan yang paling tepat?
✅ Benar! Confidence Low artinya tools tidak yakin dengan temuannya — kemungkinan false positive tinggi. Verifikasi manual diperlukan sebelum melaporkan atau memperbaiki, agar tidak membuang waktu pada isu yang tidak nyata.
❌ Kurang tepat. Confidence Low = kemungkinan false positive. Tidak boleh diabaikan (bisa jadi nyata) tapi juga tidak boleh langsung dilaporkan. Verifikasi manual adalah langkah yang tepat untuk Low Confidence alerts.
Soal 4 dari 5
Manakah tahapan yang BENAR dalam metodologi penetration testing?
✅ Benar! Urutan metodologi pentest yang benar: Scoping (definisikan target & aturan) → Reconnaissance (kumpulkan informasi) → Scanning (identifikasi kerentanan) → Eksploitasi (buktikan) → Laporan (dokumentasikan).
❌ Kurang tepat. Urutan yang benar adalah: Scoping → Reconnaissance → Scanning → Eksploitasi → Laporan. Scoping selalu pertama (tanpa aturan main, semua tindakan berikutnya tidak memiliki dasar legal).

Mengapa Fuzz Testing efektif menemukan kerentanan yang sulit ditemukan oleh SAST dan DAST biasa?
✅ Benar! SAST dan DAST bekerja berdasarkan pola yang sudah diketahui. Fuzzing mengirim input yang benar-benar acak atau di luar ekspektasi, sehingga dapat memicu crash, buffer overflow, atau perilaku tak terduga yang tidak tercover oleh signature/rules standar.
❌ Kurang tepat. Fuzzing tetap membutuhkan aplikasi yang berjalan. Keunggulannya bukan pada kedalaman analisis kode, melainkan pada input yang tidak terduga — menemukan edge case yang tidak tercakup oleh pola serangan yang sudah dikenal di SAST/DAST.
